The first buzzer wins

It’s the Christmas holidays, Alice is home, and Bob has a plan for the family quiz: a buzzer. Everyone opens a little program on their laptop or phone, and the first person to press the space bar gets to answer. He’s written it in an afternoon, it mostly works, and there’s already been an argument.

B: Grandpa pressed first. I saw him. But his buzz never arrived! A: What does your program use to send the buzz? B: UDP. You said TCP was for things that need to arrive in order, and a buzz is just one message. A: It is. But UDP doesn’t promise it’ll arrive at all. If a packet is lost on the Wi-Fi, or your laptop was too busy to read it, it’s just gone. Nobody even notices. B: Then how do I know whose press came first? Maybe his laptop’s clock is just slow. A: Everybody’s clock is slow, or fast. That’s a whole protocol of its own. It uses UDP too.

This chapter is about the transport protocol that does almost nothing: UDP, the User Datagram Protocol, which we invented in Chapter 12 as “fire and forget”. It adds only two things to IP, port numbers and a checksum, and that’s exactly why so many protocols are built on it. We’ll also look properly at how a program talks to the network in the first place, through the sockets API, and we’ll build a client for a protocol your computer uses every day, to find out what time it is.

A doorway into the kernel

Every lab in this book has used sockets, starting with Chapter 4. A program can’t touch the network card itself: only the operating system’s kernel can do that, for all the programs at once. So the kernel offers a set of system calls, functions a program can call to ask it for things. For networking, they were designed in 1983, for the version of Unix made at the University of California, Berkeley, and nearly every operating system has copied them since. A socket is two things: an entry in a table, which tells the kernel which datagrams belong to it, and a queue, where they wait until the program reads them. You can see your computer’s UDP sockets with netstat, or with lsof, which also shows which program owns each one. Here’s Bob’s MacBook, with this chapter’s time server running:

We invented UDP’s header in Chapter 12, and the real one is exactly the same:

The checksum covers the header and the data, and also the source and destination IP addresses (Chapter 12’s “pseudo-header”), so that a datagram delivered to the wrong computer is noticed. The length field allows up to 65,535 bytes, which leaves room for 65,507 bytes of data inside an IPv4 packet. But anything bigger than about 1,472 bytes won’t fit in one Ethernet frame, so IP would have to cut it into fragments (Chapter 20), and if any one fragment is lost, the whole datagram is lost. So programs that use UDP almost always keep each datagram small. The lab tries a few sizes:

What UDP doesn’t do

Here’s the whole list of what UDP does for a program: it delivers each datagram to the right socket, whole, or not at all, and it checks for damage on the way. Here’s what it doesn’t do. There’s no connection, so nobody knows whether anyone is listening. There’s no acknowledgement, so nobody knows whether a datagram arrived. There’s no numbering, so datagrams can arrive out of order, or twice. And there’s nothing to stop a sender going faster than the receiver can cope with.

That last one surprises people. It isn’t only the network that loses datagrams. The lab sends 20,000 datagrams, as fast as it can, to a socket on the same computer, and only reads them afterwards:

$ python3 udp_lab.py flood receive buffer 786,896 bytes: sent 20,000 datagrams of 1000 bytes, received ⟦1:762⟧, lost 19,238 (the kernel counted ⟦2:19,238 dropped for full buffers⟧) the survivors were numbers 0 to 761: the first ones, until the buffer filled receive buffer 8,388,608 bytes: sent 20,000 datagrams of 1000 bytes, received 8,128, lost 11,872 (the kernel counted 11,872 dropped for full buffers) the survivors were numbers 0 to 8127: the first ones, until the buffer filled 1 | The buffer holds 786,896 bytes, but only 762 datagrams of 1,000 bytes fitted: the kernel counts its own bookkeeping for each datagram too. 2 | The kernel keeps count of every datagram it throws away (netstat -s -p udp on a Mac, /proc/net/snmp on Linux), but nobody tells the sender. A bigger buffer only delays the problem.

Not one datagram was damaged, and not one crossed a network. The reader was simply too slow. That’s exactly what may have happened to Grandpa Otto’s buzz: if Bob’s program was busy drawing the screen, and the buffer was full of other people’s buzzes, his was dropped. Try it:

So a program built on UDP has to handle all of this itself, if it cares. A game sends the players’ positions many times a second, and if one update is lost, the next one replaces it anyway, so it doesn’t care. A video call would rather show a glitch than freeze while a lost packet is sent again. DNS (Chapter 29) sends its question again if there’s no answer after a second or so. Bob’s buzzer should have done the same: send each buzz a few times, with a number, and have the quizmaster’s program acknowledge it.

Connected UDP sockets

There’s one more trick hidden in the sockets API. A UDP socket can be connected. Nothing is sent: connect() just tells the kernel “this socket only talks to that address and port”. That has two effects. The kernel throws away datagrams from anyone else, and it can now tell the program about errors:

$ python3 udp_lab.py refused unconnected socket: sent fine, then silence. It never finds out nobody was there. connected socket: ⟦1:ConnectionRefusedError(61, 'Connection refused')⟧ The other computer sent back an ICMP “port unreachable” (Chapter 21), and because this socket is connected, the kernel knew which socket it was about, and told us. 1 | “Connection refused”, from a protocol with no connections! The ICMP error arrived for both sockets, but only the connected one could be matched to it.

Talking to many at once

UDP can do something TCP can’t: send one datagram to many computers. A socket with the SO_BROADCAST option can send to a network’s broadcast address, which is how DHCP’s DISCOVER works (Chapter 22). And a socket can join a multicast group, an address from 224.0.0.0/4, to receive everything sent to it. That’s how multicast DNS and Chapter 25’s neighbour discovery work, and how Bob fixes his buzzer: everyone’s program joins one group, so every buzz reaches every screen, and everyone can see who pressed first. The IP_MULTICAST_TTL of 1 keeps the chat on the home network: the first router will throw it away.

One program, many sockets

The chat has a problem that every network program meets: it has two things to wait for, the keyboard and the socket, and if it waits for one, it can’t notice the other. So it hands both to select(), a system call that waits for any of a list of sockets (or files, or keyboards) to have something ready, and says which. Its descendants, poll(), epoll on Linux and kqueue on macOS, do the same for tens of thousands of sockets at once, and they’re how a single web server handles every visitor at the same time. Python’s asyncio is built on top of them.

What time is it?

Now for Bob’s other question. Whose clock is right?

Computers keep time with a quartz crystal, like a wristwatch, and like Chapter 2’s flashlights, no two crystals tick at exactly the same speed. A typical computer clock drifts by a second or so a day. Grandpa Otto’s Raspberry Pi doesn’t even have a battery for its clock, so every time it’s switched on, it has no idea what year it is. So every computer asks the network, using the Network Time Protocol, NTP, on UDP port 123.

NTP servers form a hierarchy. At the top, called stratum 0, are real clocks: atomic clocks, and GPS receivers, which get the time from the atomic clocks in the satellites. Servers connected directly to one are stratum 1. Servers that get their time from those are stratum 2, and so on. Here’s this chapter’s lab asking five of them:

$ python3 ntp.py time.apple.com 17.253.60.45 stratum 2 offset +92.85 ms delay 98.43 ms synchronized to 17.253.68.253 time.google.com 216.239.35.12 stratum 1 offset +70.37 ms delay 54.70 ms ⟦1:GOOG (a clock of its own)⟧ time.cloudflare.com 162.159.200.1 stratum 3 offset +64.97 ms delay 15.08 ms synchronized to 10.198.8.4 pool.ntp.org 172.236.180.15 stratum 5 offset +65.32 ms delay 22.89 ms synchronized to 40.81.94.65 ntp.ubuntu.com 91.189.91.157 stratum 2 offset +60.43 ms delay 275.37 ms synchronized to 132.163.96.1 1 | A stratum 1 server names its reference clock instead of a server. Google’s just says “GOOG”; others say “GPS” or “PPS”.

Every server agrees: Bob’s MacBook is about 65 milliseconds slow. (The Mac’s own tool, sntp time.apple.com, said +0.065679.) But how can a client measure the difference between two clocks, when the answer spends an unknown time travelling across the network? With four timestamps:

The one assumption is that the journey takes as long in each direction. When it doesn’t, the answer is off by half the difference, which is why the servers with the longest delays disagree the most. Real NTP programs, like chronyd on Linux and timed on macOS, ask several servers, many times, keep the answers with the shortest delays, and throw out any server that disagrees with the rest. And they don’t jump the clock (programs get very confused when time goes backwards): they slew it, running it slightly faster or slower until it catches up. Over the internet, NTP keeps a clock within a few milliseconds. Inside data centres, where it matters more, a cousin called the Precision Time Protocol uses timestamps taken by the network cards themselves, and gets within a millionth of a second.

Why does NTP use UDP, and not TCP, which would make sure the answer arrives?

Because a late answer is worse than no answer. If a TCP packet is lost, TCP waits, and sends it again, and the answer arrives much later than it should, with no way to tell. The client would get a wildly wrong offset. With UDP, a lost request just means no answer, and the client asks again. The same goes for anything where timing matters more than completeness: voice, video, games. And a TCP connection would need three extra packets before the first question, for a conversation that’s one datagram each way.

UDP was defined in 1980, in a document just three pages long, the shortest of all the internet’s main standards. Its author was David P. Reed, who wanted a way to use IP for things that didn’t fit TCP, like speech. Today it carries DNS, DHCP, NTP, multicast DNS, voice and video calls, online games, most VPNs (Chapter 35), and, since QUIC arrived, a large share of all web traffic.

NTP is even older. David L. Mills started working on it in the early 1980s, and kept improving it for the rest of his career. Its timestamps count seconds from 1 January 1900, in 32 bits, which means they will overflow on 7 February 2036. The protocol was designed with that in mind, and most software will cope, but some old devices will get very confused about the date.

What’s next?

UDP is fire and forget, and the program has to cope with everything else. For most of what we do, loading web pages, sending email, copying files, we want every byte, in order, with nothing lost and nothing added. That’s what Chapter 13’s reliable delivery gave us, and its real version is the protocol that carries most of the internet’s traffic: TCP. Chapter 27 takes it apart, starting with a real capture of a connection that lost packets and recovered.
