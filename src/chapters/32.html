Eve moves in

Eve hasn’t given up. She’s back on Bob’s Wi-Fi, and this time she’s done what she did in Chapter 21: a forged ARP answer, so that everything Bob’s laptop sends to the router goes through her laptop first. She’s in the middle, and she can read, drop or change anything.

E: Every packet you send goes through me now. Go on, log in to your bank. B: Alice says I should just… do it. A: Look at the address bar first. What does it say? B: https://, and a padlock. E: I can see your laptop talking to the bank. I can see the name of the bank. And then… nothing. Just noise. A: Chapter 31 gave us the pieces: a key exchange you can do in public, signatures, certificates, a cipher that hides and seals. The padlock means they’ve all been put together, in a protocol called TLS. E: I could pretend to be the bank. A: Try it. That’s what the certificate is for.

TLS, Transport Layer Security, sits between TCP and the application. To the web browser it looks like an ordinary connection: bytes in, bytes out. Underneath, everything is encrypted, sealed against tampering, and tied to a certificate that proves who’s on the other end. HTTP over TLS is HTTPS, but mail, DNS (Chapter 29’s DNS over HTTPS), VPNs and almost everything else use it too. This chapter watches a real TLS 1.3 handshake, and then builds a client from scratch that fetches a real web page, with Chapter 31’s X25519 and ChaCha20-Poly1305 inside.

Notice the trick that makes it fast. Bob’s laptop doesn’t ask which kind of key exchange the server would like; it guesses (X25519, which nearly every server supports), and sends its public key in the very first message. So the server can finish the key exchange in its first reply, and encrypt everything after its hello. (If the guess is wrong, the server sends back a HelloRetryRequest saying which it wants, at the cost of an extra round trip.) TLS 1.2 needed two round trips for the same job, and sent the certificate unencrypted.

A few things stand out. The ClientHello is built out of extensions: a type, a length, and the contents, over and over. TLS has grown for thirty years by adding new ones, and servers skip any they don’t understand. And the hello tells a white lie, twice: it says “TLS 1.2” in the version field, and carries a random “session ID” it has no use for. That’s because when TLS 1.3 was being tested, a surprising number of firewalls and other boxes in the middle of the internet dropped connections that looked unfamiliar. So TLS 1.3 disguises itself as TLS 1.2 resuming an old session, and puts the real version in an extension, which those boxes ignore. Networks that refuse to let protocols change are called ossified, and it’s a big reason Chapter 33’s QUIC encrypts almost everything, even its own headers.

Proving who you are

The key exchange alone would let Bob talk privately to anyone, including Eve. What makes it the bank is three checks, all of which the lab does itself:

  1. The certificate chain. The server sends its certificate and the intermediates above it. Each must be signed by the next, up to a root the computer already trusts (Chapter 31).
  2. The name. The certificate must list the name Bob asked for (*.example.org covers any one label in front, like www.example.org, but not a.b.example.org).
  3. CertificateVerify. Anyone can send a copy of example.org’s certificate: it’s public. So the server must also sign the transcript, both key shares included, with the private key that matches the certificate. Only the real server can do that, and because the signature covers this connection’s key shares, it can’t be replayed from another one.

The lab’s certs.py reads certificates (which are written in a compact binary format called DER), and checks signatures of all three kinds the web uses, RSA, ECDSA and Ed25519, in plain Python:

What still shows

Eve can’t read the conversation, but she isn’t completely blind. She sees which IP addresses Bob talks to, when, and how much. And she sees the SNI: a hosting company like Cloudflare serves millions of sites from the same addresses, so the client must say which one it wants before any keys exist. That name is a surprisingly big leak, and some countries’ firewalls block websites by it.

The fix is Encrypted Client Hello (ECH): the site publishes a public key in DNS, in the HTTPS record from Chapter 29, and the browser encrypts its real ClientHello with it, inside an outer one that names only the hosting company:

$ python3 dig.py crypto.cloudflare.com HTTPS @8.8.8.8 --tcp ;; ANSWER: crypto.cloudflare.com. 276 HTTPS 1 . alpn=h2 ipv4hint=162.159.135.79,162.159.136.79 ⟦1:ech=(71 bytes: a public key for encrypting the ClientHello; outer name cloudflare-ech.com)⟧ … 1 | A browser that supports ECH sends “cloudflare-ech.com” in the visible SNI, and the real name, encrypted, inside. Eve learns only that Bob is visiting one of Cloudflare’s millions of sites. Of course, this only helps if the DNS question itself was private too: DNS over HTTPS, from Chapter 29.

Coming back: resumption and 0-RTT

Full handshakes cost a round trip and some public-key arithmetic. So after the handshake, servers usually send a NewSessionTicket: an encrypted note that only the server can read, holding a secret derived from this connection. Next time, the client offers the ticket in its ClientHello (as a pre-shared key, or PSK), and the server can skip the certificate and signature, because the ticket proves they’ve met before. (Clients usually do a fresh X25519 exchange alongside it too, to keep forward secrecy.)

It can even go one step further. With a ticket, the client can encrypt its request with keys from the last session, and send it along with the ClientHello, before the handshake has finished: 0-RTT, zero round trips. The catch is that Eve could record that first flight and replay it. The handshake would fail, but the server might have acted on the request already. So 0-RTT is only safe for requests that don’t matter if they’re repeated, like fetching a page, and never for “pay Bob £5”.

The session ID and “TLS 1.2” version fields are fibs, and the change_cipher_spec messages are meaningless. Why not just take them out, and let old middleboxes break?

Because the people who notice aren’t the ones who own the middleboxes. If a new browser version can’t reach a bank because the bank’s firewall is ten years old, users blame the browser, and switch to one that still works. TLS 1.3’s designers measured this carefully: early versions without the disguise failed on a few percent of connections. The lesson changed how protocols are designed: encrypt as much as you can, so that nobody in the middle can come to depend on it, and add random, meaningless values (“GREASE”) to fields, so that boxes that choke on unknown values get fixed early.

Netscape built SSL in 1994 for the first online shops. SSL 2.0 had serious flaws, and SSL 3.0 was a redesign. The standards body took it over in 1999 and renamed it TLS 1.0, followed by 1.1 (2006), 1.2 (2008) and, after four years of work, 1.3 in 2018, which removed every old option that attacks had been found in. The web went from well under half of all page loads being encrypted in the mid-2010s to over 95% today, mainly thanks to free certificates from Let’s Encrypt and browsers marking plain HTTP pages “not secure”.

TLS itself has held up well; most famous disasters were in the software around it. In 2014, a bug called Heartbleed in OpenSSL let anyone read chunks of a server’s memory, private keys included, from about a sixth of the web’s servers. That’s a big reason why the lab uses its homemade crypto for learning only.

What’s next?

Eve packs up her laptop. She can’t read it, she can’t change it, and she can’t pretend to be the bank. But look again at curl’s output: “ALPN: server accepted h2”. Inside the tunnel, browsers today mostly don’t speak Chapter 30’s HTTP/1.1 at all. They speak HTTP/2, a binary version that sends many requests at once over one connection, or HTTP/3, which leaves TCP behind entirely and runs over a new protocol on UDP, with TLS built in. Chapter 33 takes them apart.
