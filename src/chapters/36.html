Too many things on one Pi

Grandpa Otto’s Pi is getting crowded. It serves the garden website. It streams the slug camera. Bob has added a little program that checks the weather forecast every hour and emails Grandpa when frost is coming, and a database of everything Grandpa has ever planted.

B: The camera’s web page wants port 80. So does the garden website. And last night the weather bot had a bug, opened thousands of connections, and took everything else down with it. A: They’re all sharing one network: one set of addresses, one set of ports, one firewall. Give each of them its own. B: Four Pis? A: One Pi, pretending to be four. Each program in a box, with its own network card, its own address, its own ports. Plugged into a switch that only exists in software. B: That sounds like what Docker does. A: It is exactly what Docker does. Let’s do it by hand first.

A container is a program running in a box of its own: its own files, its own list of processes, its own hostname, and, the part this chapter is about, its own network. It isn’t a separate computer, and not even a virtual one: it’s an ordinary process, which the Linux kernel shows a different view of the machine. Docker, Podman and Kubernetes are, underneath, tools for setting up those views. We’ve already used the network part twice without explaining it: Chapter 34’s firewall and Chapter 35’s two houses both lived in network namespaces.

A network of your own

Any process can ask the kernel for a fresh network namespace, with a single system call, unshare. Python 3.12 can call it directly. This chapter’s nsdemo.py takes port 8080 on the Pi, then starts a child process, which asks for a new namespace and looks around:

$ sudo python3 nsdemo.py this process, on the host: devices: lo, eth0, wlan0 port 8080: Address already in use; can reach 1.1.1.1 a child, after unshare(NEWNET): devices: ⟦1:lo⟧ ⟦2:port 8080 is free⟧; can't reach 1.1.1.1 (Network is unreachable) …after switching on its loopback: devices: lo port 8080 is free; can't reach 1.1.1.1 (Network is unreachable) the host again (unchanged): devices: lo, eth0, wlan0 port 8080: Address already in use; can reach 1.1.1.1 1 | A brand-new namespace has nothing in it but a loopback interface, switched off: no Wi-Fi, no addresses, no routes. It’s like a computer with its network card pulled out. 2 | Port 8080 is taken on the host, and free here: ports belong to namespaces, not to the computer. So every container can have its own web server on port 80.

Namespaces aren’t only for containers. Look at what lsns lists on the Pi, before we’ve made any of our own:

$ lsns -t net NS TYPE NPROCS PID USER NETNSID NSFS COMMAND 4026531833 net 209 1 root unassigned /sbin/init splash 4026532596 net 1 834 polkitd unassigned ├─/usr/lib/polkit-1/polkitd --no-debug --log-level=notice 4026532597 net 1 704 root unassigned └─/usr/libexec/accounts-daemon

Everything runs in the first one, except two system services, which systemd has quietly put into empty network namespaces of their own: they never need the network, so if anyone ever breaks into them, they can’t use it either.

Virtual cables and a software switch

An empty namespace is safe, but useless. To connect it, Linux offers a veth pair: two virtual network interfaces joined like the two ends of a cable. Whatever goes in one end comes out of the other, and each end can live in a different namespace. And to connect several namespaces at once, there’s a bridge: Chapter 9’s learning switch, as a piece of software, with virtual cables plugged into it. This chapter’s box.sh builds three boxes, web, db and bot, like this:

Getting out, and getting in

The boxes can talk to each other, but not to the world: their addresses, 10.36.0.x, mean nothing outside the Pi. Two more pieces fix that, and you’ve met both. The host becomes the boxes’ router (they all have a default route to 10.36.0.1), with forwarding switched on, and it does NAT, exactly like the home router in Chapter 22: going out, it swaps their private source addresses for its own. And to let the world in, a destination NAT rule “publishes” a port: connections to the Pi’s port 8036 are rewritten to go to the web box’s port 80:

== out to the internet, through the host's NAT bot → https://example.org: HTTP 200, from ⟦1:10.36.0.4⟧ to 104.20.26.136 == the NAT, remembered by conntrack tcp 6 119 FIN_WAIT src=10.36.0.4 dst=104.20.26.136 sport=36680 dport=443 src=104.20.26.136 ⟦2:dst=192.168.1.4⟧ sport=443 dport=36680 [ASSURED] … $ curl http://192.168.1.4:8036/ Hello from the web box $ sudo conntrack -L -p tcp --dport 8036 tcp 6 119 TIME_WAIT src=192.168.1.3 dst=192.168.1.4 sport=62019 ⟦3:dport=8036⟧ ⟦4:src=10.36.0.2⟧ dst=192.168.1.3 sport=80 dport=62019 [ASSURED] … 1 | The bot thinks it’s 10.36.0.4… 2 | …but replies come back to 192.168.1.4, the Pi: the masquerade rule rewrote the source on the way out. (And then the home router rewrote it again, to the public address.) 3 | The Mac connected to the Pi’s port 8036… 4 | …and the reply really comes from the web box, on port 80. conntrack turns it back into “192.168.1.4:8036” before the Mac sees it.

What Docker and Podman do

That’s all a container runtime does for networking, automatically, every time: docker run makes a namespace, a veth pair, plugs one end into a bridge (docker0), gives the container an address, and adds NAT rules; -p 8036:80 adds the DNAT rule. They add one more thing on their own networks: a small DNS server, so containers can find each other by name. Here are two containers on a Podman network on Bob’s MacBook, one fetching a page from the other:

$ podman network create garden $ podman network inspect garden --format '{{range .Subnets}}{{.Subnet}} gw {{.Gateway}}{{end}} dns={{.DNSEnabled}} iface={{.NetworkInterface}}' 10.89.0.0/24 gw 10.89.0.1 dns=true iface=⟦1:podman1⟧ $ podman run -d --network garden --name web alpine sh -c 'while true; do printf "HTTP/1.0 200 OK\r\nContent-Length: 29\r\n\r\nHello from the web container\n" | nc -l -p 80; done' $ podman run --rm --network garden --name db alpine sh -c 'ip -o -4 addr show eth0; ip route; nslookup web | grep -A1 ^Name; wget -qO- http://web/' 2: eth0 inet ⟦2:10.89.0.5/24⟧ brd 10.89.0.255 scope global eth0 default via 10.89.0.1 dev eth0 metric 100 10.89.0.0/24 dev eth0 scope link src 10.89.0.5 Name: ⟦3:web.dns.podman⟧ Address: 10.89.0.4 Hello from the web container 1 | The bridge: box.sh’s br36, with a different name. 2 | The container’s eth0, the inside end of a veth pair. 3 | Podman’s DNS server, listening on the bridge’s own address, knows every container on the network by name.

Kubernetes: networks for fleets

Docker and Podman manage the containers on one computer. Kubernetes runs thousands of them across hundreds of computers, starting, stopping and moving them as computers fail and demand changes. Its networking is the same pieces again, at a larger scale:

Two more ideas complete it. A NetworkPolicy is a firewall per pod (“only the garden pods may talk to the database”), written once, and turned into rules on every node. And an Ingress or Gateway is a layer 7 load balancer (Chapter 34) at the cluster’s edge, which ends TLS and sends each request to the right Service by its name and path. Almost everything in this part of the book, from ARP to BGP, VXLAN, NAT, DNS and load balancing, is running inside a Kubernetes cluster at once.

People often call containers “lightweight virtual machines”. From the network’s point of view, what’s the real difference?

A virtual machine has its own kernel: its own TCP, its own firewall code, its own drivers for a pretend network card. A container shares the host’s kernel, and only gets its own view of it. That’s why containers start in milliseconds and cost almost nothing, and it’s also why some limits are shared. All of box.sh’s boxes use the host’s conntrack table, for instance, whose size is fixed: a container that opens a million connections can fill it, and then new connections fail in every container on the computer, which is roughly what Bob’s weather bot did. And a bug in the kernel’s network code is a bug in every container at once.

The idea is old. Unix got chroot, which gives a program its own view of the files, in 1979; FreeBSD’s “jails” added separate networking in 2000. Linux gained namespaces one kind at a time from 2002, with network namespaces arriving around 2008 and 2009, and control groups (limits on memory and processor time) at about the same time. None of it was easy to use until Docker, in 2013, wrapped it all in a single command, and added a simple way to package a program with everything it needs.

Kubernetes came from Google in 2014, based on its internal system Borg, which had been running all of Google’s services in containers for a decade. Its rule that every pod gets a routable address of its own was a reaction to Borg, where programs shared their computer’s address and had to be given ports, which made everything else complicated.

A Raspberry Pi is ideal. On a Mac or Windows, Docker Desktop or Podman shows the same ideas from the outside (experiment 4).

1. Containers by hand

sudo ./box.sh builds the three boxes, tests them, shows the bridge, the NAT and the namespaces, and removes everything again. sudo ./box.sh keep leaves them running, so you can explore: sudo ip netns exec db bash gives you a shell inside the db box (type exit to leave), and from another computer, curl http://your-pi:8036/ reaches the web box. sudo ./box.sh down tidies up.

2. Namespaces from Python

sudo python3 nsdemo.py makes a namespace with unshare. With the boxes running, sudo python3 nsdemo.py web steps into one with setns, which is what ip netns exec and docker exec do:

$ sudo python3 nsdemo.py web this process, on the host: devices: lo, eth0, wlan0, br36, veth-web, veth-db, veth-bot port 8080 is free; can reach 1.1.1.1 after setns() into “web”: devices: lo, eth0 port 8080 is free; can reach 1.1.1.1 and its addresses and routes, from inside: lo UNKNOWN 127.0.0.1/8 ::1/128 eth0@if59 UP 10.36.0.2/24 fe80::b872:d6ff:feba:cdac/64 default via 10.36.0.1 dev eth0 10.36.0.0/24 dev eth0 proto kernel scope link src 10.36.0.2

Experiments

  • With the boxes running, capture on the bridge (sudo tshark -i br36) while the db box fetches from the web box. Then capture on wlan0 while the bot box fetches example.org. Which addresses appear where?
  • Delete the masquerade rule (sudo nft flush chain ip box36 post) and try to reach the internet from the bot box. The packets still leave (check with tshark on wlan0): why does no answer ever come back?
  • Make a second bridge, br37, with its own box, on 10.37.0.0/24. Can it reach the boxes on br36? What would you have to add? (That’s what separate Docker networks give you: isolation by default.)
  • With Docker or Podman: docker run --rm alpine ip route, and then docker run --rm --network host alpine ip route. What changed, and what did the container give up?
