Eighty photos

Grandpa Otto has discovered the photo gallery. His garden website now has a page with eighty pictures of beans, and it’s the page he shows everyone, on his phone, standing at the allotment where the mobile signal comes and goes.

B: The page itself is fast now, with caching. But look at the waterfall in the developer tools: the photos load six at a time. The rest just sit there, “queued”. A: That’s HTTP/1.1. One request at a time on each connection, and the browser won’t open more than six to one site. B: Couldn’t it send all eighty requests down one connection? A: It could send them, but the answers would have to come back in order, one whole photo after another. One slow photo holds up everything behind it. B: So what we want is one connection, with all eighty photos coming back at the same time, mixed together. A: Chopped into pieces, with a label on each piece saying which photo it belongs to. That’s HTTP/2. And then there’s the problem of the signal at the allotment…

Chapter 30’s HTTP/1.1 is still spoken everywhere, but most requests from a modern browser now use one of its two successors. HTTP/2 keeps everything HTTP means (methods, headers, status codes, caching) but sends it as binary frames, so many requests can share one connection. HTTP/3 goes further and replaces TCP itself, with a new transport protocol called QUIC, built on UDP, with TLS 1.3 inside. In this chapter we take both apart, and build clients for each, from scratch.

HTTP/1.1’s traffic jam

An HTTP/1.1 connection is a conversation where only one question can be in the air at a time. A response must be completely sent before the next can start, because there’s nothing in the bytes to say which response they belong to. That’s head-of-line blocking: the response at the front of the line holds up everything behind it.

Browsers work around it by opening several connections to the same site, up to six, each with its own TCP handshake, TLS handshake and slow start (Chapter 28). Websites worked around it with tricks: spreading files over several domain names to get six connections each, gluing small images into one big one, and pasting scripts and styles straight into the page. HTTP/2 made all of those unnecessary.

Frames and streams

An HTTP/2 connection starts like any HTTPS connection, except that in the TLS handshake, the browser’s ALPN extension (Chapter 32) offers h2, and the server accepts. After that, everything is frames, each with a 9-byte header:

The stream number is the label on each piece. Each request and its response is a stream: the client picks a new odd number for each request (1, 3, 5…), sends a HEADERS frame with the request’s headers, and the response comes back as HEADERS and DATA frames with the same number. Frames of different streams can be mixed together in any order. Here’s this chapter’s lab, an HTTP/2 client written directly on top of Python’s TLS, asking example.org for its page:

A few more frame types do the housekeeping. RST_STREAM cancels one request (you scrolled away from a photo) without closing the connection. PING checks the connection is alive and measures the round trip. GOAWAY closes the connection politely, saying which streams were handled. And browsers can say which responses matter most, so that the page’s stylesheet comes before a photo at the bottom. HTTP/2 also had server push, letting a server send files the browser hadn’t asked for yet, but it was hard to use well, often sent files the browser already had, and browsers have since removed it.

Squeezing the headers

Every request carries much the same headers: the same site, the same user-agent, the same cookies. HTTP/2 compresses them with HPACK, which works three ways:

  • A static table of 61 common headers, built into the standard: :method: GET is entry 2, :status: 200 is entry 8. Sending one costs a single byte.
  • A dynamic table that both ends build as the connection goes on: a header sent once can be added to it, and later referred to by number.
  • A Huffman code for the text that remains, which gives common characters (like lowercase letters and digits) shorter bit patterns than rare ones, like Chapter 1’s Morse code.
$ python3 hpack.py request 1: 50 bytes of headers (about 129 as HTTP/1.1 text) 1 bytes :method: GET ⟦1:index 2⟧ 1 bytes :scheme: https index 7 14 bytes :authority: en.wikipedia.org ⟦2:name index 1, value Huffman-coded, remembered⟧ 12 bytes :path: /wiki/HTTP/2 name index 4, value Huffman-coded, remembered 13 bytes user-agent: bitbybit-h2/1.0 name index 58, value Huffman-coded, remembered 9 bytes accept: text/html name index 19, value Huffman-coded, remembered request 2: ⟦3:17 bytes of headers⟧ (about 129 as HTTP/1.1 text) 1 bytes :method: GET index 2 1 bytes :scheme: https index 7 1 bytes :authority: en.wikipedia.org ⟦4:index 65⟧ 12 bytes :path: /wiki/HTTP/3 name index 4, value Huffman-coded, remembered 1 bytes user-agent: bitbybit-h2/1.0 index 64 1 bytes accept: text/html index 63 1 | In the static table: one byte. 2 | The name is in the static table, the value isn’t, so it’s sent as Huffman-coded text (16 letters in 13 bytes), and both sides add the whole header to their dynamic tables. 3 | The second request is a third the size: only the path is new. 4 | Dynamic table entries are numbered from 62, newest first.

The headers look like a detail, but they add up: a page that makes a hundred requests with a kilobyte of cookies each would send 100 KB of headers, before any content. The design is also careful about security. HTTP/2’s predecessor, SPDY, compressed headers with ordinary gzip, until an attack called CRIME showed that an attacker who could add text to your requests could guess your cookies, a letter at a time, by watching whether the compressed size shrank. HPACK only reuses whole headers, never pieces of them, and lets sensitive ones be marked “never index”.

The jam moves down a layer

HTTP/2 fixed head-of-line blocking in HTTP. But it’s all on one TCP connection, and TCP delivers one stream of bytes, strictly in order. If one packet is lost, every byte after it waits in the receiver until the resend arrives, even bytes that belong to completely different responses. The fix needs a transport that knows about streams, and can hand over each one’s data as soon as that stream is complete, whatever’s missing from the others. And while we’re replacing TCP, we could fix the other thing the widget shows: two round trips of handshakes before the first request.

QUIC: TCP, rebuilt on top of UDP

Why not just improve TCP? Because TCP lives in the operating system of every computer, phone and router, and changes to it take a decade to spread. Worse, the middleboxes of Chapter 32, firewalls and NATs and “helpful” accelerators, look inside TCP headers, and drop anything that doesn’t look like the TCP they know. New TCP options have been designed that simply don’t work on much of the internet.

So QUIC starts from UDP, which middleboxes let through untouched (Chapter 26: just ports and a length), and builds everything else on top, in the application itself: connections, streams, reliable delivery, flow control and congestion control (it uses the same ideas as Chapter 28: slow start, CUBIC or BBR). TLS 1.3 isn’t layered on top, it’s built in: the TLS handshake messages travel inside QUIC’s own packets, and the keys it produces encrypt every packet. And QUIC encrypts almost all of its own header too, so no middlebox can come to depend on it:

A QUIC connection has three stages, each with its own keys and its own kind of packet: Initial packets carry the ClientHello and ServerHello; Handshake packets carry the rest of the TLS handshake; and 1-RTT packets carry everything after. Inside each packet are frames, much like HTTP/2’s: CRYPTO frames for TLS messages, STREAM frames for data, ACK frames for acknowledgements, and a few more. HTTP/3 then sends its own small frames (HEADERS and DATA) on QUIC’s streams, with the header compression reworked into QPACK, because streams can now arrive out of order.

Two things about QUIC are surprising. They don’t hide anything from Eve; they’re there so that nothing in the middle can read or quietly change QUIC’s first packets, and come to depend on what’s inside. Finding HTTP/3

A browser can’t know in advance that a server speaks QUIC: it’s a different protocol, on UDP instead of TCP. There are two ways to find out. The server can say so in a header over an ordinary HTTPS connection, Alt-Svc: h3=":443", as Google did above, and the browser remembers it for next time. Or the site’s DNS can say so up front, in the HTTPS record from Chapter 29:

$ python3 dig.py cloudflare.com HTTPS @8.8.8.8 --tcp cloudflare.com. 300 HTTPS 1 . ⟦1:alpn=h3,h2⟧ ipv4hint=104.16.132.229,104.16.133.229 ipv6hint=2606:4700::6810:84e5,2606:4700::6810:85e5 1 | “I speak HTTP/3 and HTTP/2.” The browser can try QUIC on its very first visit.

Browsers still race a TCP connection alongside, in case UDP is blocked, which it often is on company and school networks, whose firewalls only understand TCP. On Bob’s MacBook, with Chrome open, you can see its QUIC connections as plain UDP sockets:

Changing networks mid-sentence

Because a QUIC connection is named by its connection ID, and not by addresses and ports, it can survive something no TCP connection can: moving to a different network.

Is it faster?

The honest answer: it depends on the path. QUIC saves one round trip on every new connection (and returning visitors can send their request in the very first packet, with 0-RTT, subject to the same replay caveat as Chapter 32), and it stops one lost packet from stalling every stream:

On a short, clean path the saving disappears into the noise: from the Pi to Cloudflare, 10 ms away, HTTP/2 and HTTP/3 both deliver the first byte in about 70 ms, most of it the server thinking. Across 175 ms, the saved round trip is worth a hundred milliseconds on every new connection, and on lossy mobile networks the difference in stalls matters more still. On the other side of the scales, QUIC costs more processing: TCP is handled in the operating system, often with help from the network card, while QUIC encrypts every packet header in the application. Big websites think it’s worth it, which is why a large share of the web’s traffic now travels over QUIC.

QUIC is built on UDP, which means every QUIC packet carries an 8-byte UDP header that does almost nothing. Why not make QUIC its own protocol, with its own number in the IP header, next to TCP (6) and UDP (17)?

Because it wouldn’t get through. Home routers’ NAT (Chapter 22) needs ports to know which device a packet belongs to, and only knows how to find them in TCP and UDP. Firewalls block protocols they don’t recognise. This has been tried: a protocol called SCTP, standardized in 2000 with many of QUIC’s ideas (several streams in one connection, and several addresses), works well inside telephone networks, and almost nowhere on the public internet. UDP is QUIC’s disguise, and eight bytes is a small price.

Google designed SPDY (“speedy”) in 2009 and tested it in Chrome against its own servers, where it could change both ends at once. It became the basis of HTTP/2, standardized in 2015. Google then started on QUIC in 2012, again testing in Chrome and on YouTube and Search, and in 2016 handed it to the standards body, which reworked it heavily, most visibly by replacing Google’s own cryptography with TLS 1.3. QUIC version 1 was published in 2021, and HTTP/3 in 2022.

QUIC isn’t only for the web. DNS can run over it (“DNS over QUIC”), so can SSH-like remote shells, and video calls and games use its “unreliable datagram” extension, for data that’s useless if it arrives late.

What’s next?

Look at who answered every request in this chapter and the last: server: cloudflare, Google’s sffe, headers like cf-cache-status: HIT. Hardly any of them came from the website’s own computer. Between Bob and almost every website sit machines that answer on its behalf, cache its pages, spread its visitors across hundreds of servers, and stop attacks before they arrive. Chapter 34 meets the middlemen: proxies, load balancers, content delivery networks and firewalls.

Experiments

  • Try python3 quic.py get www.facebook.com /. The server hangs up at once, with error 0x128: a TLS alert, number 40, “handshake failure”.
