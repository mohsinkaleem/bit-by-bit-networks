Running out of room

Carol has drawn a volcano for Alice’s class presentation. It’s a good volcano, with smoke puffing out of the top. Alice wants to send it to Bob so he can add it to their slides, and she immediately hits a wall.

Our computers still speak the codebook from Chapter 1: 26 capital letters, a space, four punctuation marks and a squiggle. That’s all 5 bits can hold. There are no lowercase letters and no digits. Carol’s name has no é in it, but plenty of names do. And the codebook has no way at all to describe a picture.

We need a much bigger vocabulary. Fortunately, Chapter 1 already told us how to get one. Every extra bit doubles the number of things we can say:

  • 6 bits: 64 symbols. Enough for upper and lowercase, but not much else.
  • 7 bits: 128 symbols. Room for letters, digits, punctuation and some control codes.
  • 8 bits: 256 symbols. All of that, with room to spare.

Eight is great

Computers settled on 8 bits as their basic unit, and a group of 8 bits is called a byte. Why 8? Partly because it’s a power of two, which makes the hardware simpler: 8 bits split neatly into two halves of 4, and those split into 2s. Partly because 256 values turned out to be enough for a character set, a pixel’s brightness or a small number, all at once. And partly, honestly, because one very influential computer did it that way and everybody followed.

From now on, when our computers send data, they send bytes: 8 bits at a time. Here’s a byte to play with. Flip the bits and watch the number and the character change (we’ll get to the character table in a moment):

The word byte was coined by Werner Buchholz at IBM in 1956, spelled with a “y” so nobody would confuse it with bit. Early computers had bytes of all sorts of sizes, and 6 bits was common. IBM’s hugely successful System/360 settled on 8 in 1964, and the rest of the industry followed. Networking standards still often say octet when they mean “exactly 8 bits, no arguments”.

Watch out for one trap you’ll meet constantly. Network speeds are measured in bits per second, but file sizes are in bytes. A “100 Mbit/s” internet connection moves at most 100 ÷ 8 = 12.5 megabytes per second. And you may also see kibibytes (KiB), which are 1,024 bytes instead of 1,000, because 1,024 is a power of two.

Hex marks the spot

Writing bytes in binary gets tiresome fast. 01001000 01101001 is only two bytes, and it’s already hard to read. Decimal is shorter (72, 105), but you can’t see the bits in it any more.

Programmers use a compromise called hexadecimal, or hex: base 16. Chop a byte into two halves of 4 bits. Each half has 16 possible values, from 0000 to 1111, so it can be written as a single “digit”. We only have ten digit symbols, so we borrow letters for the rest: A means 10, B means 11, and so on up to F for 15.

So every byte is exactly two hex digits, from 00 to FF (255). Hex numbers are often written with a 0x in front, like 0x48, so you don’t mistake them for decimal. You’ll see hex everywhere in networking: in addresses, packet dumps, colors and error codes. It’s worth getting comfortable with.

A table everyone agrees on

Remember what made the codebook work: Alice and Bob had the same table. With 256 possible byte values, the whole world needs the same table, or a byte sent from one computer will turn into a different letter on another.

The table almost everyone agreed on is called ASCII, the American Standard Code for Information Interchange, from 1963. It uses the first 128 values (7 bits’ worth), and here it all is:

A few things worth noticing:

  • The first 32 codes aren’t printable characters at all. They’re control codes from the teleprinter era, with exactly the jobs our ~ codes had: STX and ETX (start and end of text), ACK and NAK, LF (line feed, our ~L), even BEL, which rang a real bell on the teleprinter.
  • Digits are in order and start at 0x30, so the digit 7 is 0x37. The character “7” and the number 7 are different bytes!
  • “A” is 0x41 and “a” is 0x61. They differ by exactly 32, a single bit. Flipping that one bit switches between upper and lowercase, which made case-insensitive comparison easy for 1960s hardware.
  • Our trusty ~ is 0x7E, or 01111110 in binary. That happens to be the same byte PPP uses as its frame marker (Chapter 3). A lucky coincidence, but a fitting one.

Café, 日本, 👋

ASCII is great for English, but it has no é, no ñ, no Greek, Arabic, Hindi or Chinese, and certainly no emoji. For decades, different countries filled bytes 128–255 with their own letters, which meant a document written on a Russian computer came out as gibberish on a French one. And 256 slots were never going to be enough for Chinese, which has tens of thousands of characters.

The fix came in two parts. First, Unicode gives every character in every writing system a number of its own, called its code point. “A” is U+0041 (the same as ASCII), é is U+00E9, 日 is U+65E5, and 👋 is U+1F44B. There are over 150,000 of them so far.

Second, UTF-8 is a clever way of turning those numbers into bytes. Small numbers (the ASCII characters) take one byte, exactly as before, so old English text is still valid UTF-8. Bigger numbers take two, three or four bytes, and the first bits of each byte say how many bytes the character uses:

Notice that a byte starting with 10 is always a “continuation” byte, never the start of a character. So if a receiver joins in partway through a stream, it can skip forward to the next byte that doesn’t start with 10 and be back in sync. It’s a little like the start pulses from Chapter 2, built into the encoding itself.

UTF-8 was designed by Ken Thompson and Rob Pike in 1992. The story goes that they sketched it on a placemat in a New Jersey diner. Today about 98% of all web pages are UTF-8. One practical consequence: “how long is this text?” has more than one answer. "👋" is 1 character, 1 code point and 4 bytes. Some characters are even built from several code points: é can be stored as one code point, or as “e” plus a separate combining accent. Networks move bytes, so when a protocol says a field can be “at most 255 long”, always check whether it means characters or bytes.

Pictures are just numbers

Now for Carol’s volcano. A picture on a screen is a grid of tiny squares called pixels. To send a picture, we just need to describe every pixel with a number, row by row.

The simplest pictures are black and white: each pixel is either dark or light. That’s one bit per pixel, so a row of 8 pixels fits exactly into one byte. Try it:

Grayscale pictures use a whole byte per pixel: 0 for black, 255 for white, and 254 shades in between. Color pictures use three bytes per pixel, one each for how much red, green and blue light to mix, from 00 (none) to FF (full). Mixing those three gives 256 × 256 × 256, about 16.7 million colors:

That adds up quickly. A photo on a typical HD screen is 1920 × 1080 pixels × 3 bytes, over 6 megabytes. That’s why pictures are usually compressed. PNG files squeeze out repetition without losing anything (Carol’s volcano, with its big flat areas, shrinks enormously). JPEG files go further by quietly throwing away detail your eye won’t miss. Either way, it’s still just bytes.

Where does a picture end?

Alice tries to send the volcano with our trusty protocol from Chapter 4, and it goes horribly wrong. Bob gets a picture that stops a third of the way down.

The problem is framing. Our messages end with the control code ~E. But a picture is just bytes, and any byte value can turn up in it, including 0x7E, the byte for ~. The first time the picture happens to contain ~E, Bob’s computer thinks the message is over.

Escaping still works, since we can double every ~ byte. But it has costs. The sender has to inspect every single byte to find the ~s, the receiver has to inspect every byte again to undo it, and the message gets longer by an amount you can’t predict in advance. For big pictures and videos, that’s a lot of fiddling.

There’s a much simpler approach: say how long the data is before sending it. If the message begins with “944 bytes are coming”, the receiver doesn’t need to look for an end marker at all. It counts 944 bytes and stops. The data can contain anything whatsoever.

The catch is that the sender needs to know the length before it starts, which is fine for a file on disk but awkward for something being generated on the fly (we’ll meet a fix in Chapter 7). For files, the length approach wins.

Since our messages now carry several pieces of information about the data (its length, and in a moment its type), Alice and Bob tidy up the format. From now on, a reply looks like this: a status line, then any number of header lines of the form Name: value, then a blank line, and then exactly Length bytes of body.

status | OK header | Type: image/png header | Length: 944 blank | (an empty line: headers are over) body | 89 50 4E 47 0D 0A 1A 0A 00 00 00 0D 49 48 44 52 … (944 bytes)

Because headers are just lines of text, it’s easy to add new ones later, and a receiver can simply skip any header it doesn’t understand. That flexibility will matter a lot.

Which end first?

There’s a second, quieter question hiding in “Length: 944”. We wrote the length as text, the three characters “9”, “4”, “4”. Many protocols instead store numbers directly as binary, which is shorter and faster for computers to handle. But 944 is bigger than 255, so it doesn’t fit in one byte. It needs two: 0x03 and 0xB0. Which one do you send first?

Either order works, as long as both sides agree. Sending the “big end” first, the way we write numbers, is called big-endian. Sending the small end first is little-endian. Awkwardly, most computers today store numbers little-endian in memory, while internet protocols send them big-endian. So every networked program is constantly flipping bytes around, and forgetting to is a classic bug: 1000 read in the wrong order comes out as 59,395.

The terms come from Gulliver’s Travels, where the empires of Lilliput and Blefuscu go to war over which end of a boiled egg to crack. Computer scientist Danny Cohen borrowed them in a 1980 note titled “On Holy Wars and a Plea for Peace”, arguing that the choice matters far less than everybody agreeing. The internet agreed on big-endian, which is why it’s also called network byte order.

What am I looking at?

One last problem. Bob receives 8 bytes: 48 45 4C 4C 4F 21 21 21. Is that the text “HELLO!!!”, or an 8×8 black-and-white picture? Load the “HELLO!!!” preset into the pixel editor above: it’s both! The bytes themselves don’t say what they mean. Only the sender knows.

So the sender has to tell the receiver, with one more header: Type. Rather than invent our own names, we’ll use the same scheme the internet does, a general category, a slash, and a specific format:

  • text/plain: plain text (and it’s polite to say which encoding: text/plain; charset=utf-8)
  • image/png, image/jpeg: pictures in those formats
  • audio/mpeg: an MP3 file
  • application/octet-stream: “just bytes; I don’t know what they are either”

With Type and Length, Bob’s computer knows exactly how many bytes to read and what to do with them: show text, display a picture, play a sound.

These names are called media types, or MIME types. They were invented in 1992 so that email could carry attachments (MIME stands for Multipurpose Internet Mail Extensions), and the web adopted them wholesale. Every web page your browser loads arrives with a Content-Type header.

Many file formats also label themselves, by starting with a few fixed bytes called a magic number. Every PNG file begins with 89 50 4E 47 (the last three are “PNG” in ASCII). JPEGs start with FF D8 FF, PDFs with %PDF, and ZIP files with PK, the initials of Phil Katz, who created the format. The file command on your Mac identifies files this way.

What’s next?

Our computers now speak in bytes. They can send text in any language, pictures, sounds, or anything else, with headers saying how long the data is and what it is. Carol’s volcano makes it into the slides, and it’s a hit.

Which brings us back to the problem from the end of the last chapter. Bob’s report says “see SCHEDULE”, and Alice has to fetch it by hand. She doesn’t even know what files Bob has. In the next chapter we’ll fix that by letting documents point at each other, and in the process build something that will look very familiar.
