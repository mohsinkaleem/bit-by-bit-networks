Two computers, one address

Bob has bought a printer. The instructions said to give it an address, so he typed in one that looked free: 192.168.1.7. Everyone can print. But Alice, who is still home for the weekend, keeps losing her Wi-Fi connection, and her laptop has started showing a warning: “Another device on the network is using your computer’s IP address.”

A: Bob. What address did you give the printer? B: 192.168.1.7. It wasn’t being used. A: It was being used by me! The router gave it to my laptop on Friday. Now whenever someone asks “who has 192.168.1.7?”, two cards answer, and whichever answers last wins. B: How did your laptop even notice? A: It asked the network “does anyone else have my address?” when it joined. And it keeps listening for anyone claiming it. The “who has?” messages from Chapter 11 are more useful, and more dangerous, than they look.

Every protocol so far has been about carrying somebody’s data. This chapter is about two small protocols that carry almost none: they’re the network talking about itself. ARP is how a computer finds the card address for an IP address on its own network. ICMP is how routers and computers report problems, and how ping and traceroute work.

“Who has?”, for real

In Chapter 20, the Pi decided that 192.168.1.1 isn’t on its network, so its packet to 1.1.1.1 had to go to the router. But the Pi’s Wi-Fi card can only send frames to card addresses, and it only knows the router’s IP address. The Address Resolution Protocol fills the gap, exactly as we invented it in Chapter 11. The question goes to everyone, because the Pi doesn’t know who to ask. The answer comes straight back, because now the router knows exactly where the Pi is: its card address was in the question. And the router also remembers the Pi, since a computer that’s asking about you is probably about to talk to you. You can watch it happen with arping on Linux, which sends “who has?” questions the way ping sends pings:

$ sudo arping -c 3 -I wlan0 192.168.1.1 ARPING 192.168.1.1 from 192.168.1.4 wlan0 Unicast reply from 192.168.1.1 [14:c3:5e:40:0b:32] 6.343ms Unicast reply from 192.168.1.1 [14:c3:5e:40:0b:32] 4.630ms Unicast reply from 192.168.1.1 [14:c3:5e:40:0b:32] 4.669ms Sent 3 probes (⟦1:1 broadcast(s)⟧) Received 3 response(s) 1 | Only the first question was a broadcast. Once arping knew the answer, it asked the router directly, to check it was still there. Computers do the same with their own entries before they expire.

A memory that fades

Asking before every single packet would be slow, so every computer keeps an ARP cache of the answers. But it can’t keep them forever, because devices leave and addresses are reused. Linux keeps careful track of how sure it is about each entry:

$ ip neigh 192.168.1.3 dev wlan0 lladdr e2:5f:b1:3c:77:0a ⟦1:STALE⟧ 192.168.1.1 dev wlan0 lladdr 14:c3:5e:40:0b:32 ⟦2:REACHABLE⟧ 1 | STALE: the Pi hasn’t heard from Bob’s laptop for a while. It will still use the entry, but if it sends something, it will check the answer is still right soon after (DELAY, then PROBE). 2 | REACHABLE: confirmed recently, about 30 seconds ago at most. If a check gets no answer, the entry becomes FAILED and is thrown away.

Macs are more relaxed, and keep entries for up to 20 minutes. Either way, when a device changes its card, as when Bob replaced the doorbell, other computers find out within minutes.

There are two special kinds of ARP message. When a computer gets an address, it first sends a probe: “who has 192.168.1.7?”, with its own address left as 0.0.0.0, so as not to confuse anyone. If someone answers, the address is taken. That’s how Alice’s laptop noticed the printer. Then it sends an announcement (also called a gratuitous ARP): an answer to a question nobody asked, “192.168.1.7 is at my card”, so everyone updates their caches at once. Here’s the Pi checking whether anyone else has its address:

$ sudo arping -D -c 2 -I wlan0 192.168.1.4 ARPING 192.168.1.4 from ⟦1:0.0.0.0⟧ wlan0 Sent 2 probes (2 broadcast(s)) Received ⟦2:0 response(s)⟧ $ sudo tcpdump -i wlan0 -n -e arp 03:13:56.973119 2c:cf:67:5e:10:c2 > ff:ff:ff:ff:ff:ff, ethertype ARP (0x0806), length 42: Request who-has 192.168.1.4 (ff:ff:ff:ff:ff:ff) tell ⟦1:0.0.0.0⟧, length 28 1 | A probe: “I’m not claiming any address yet.” 2 | Nobody else has 192.168.1.4. If the printer had been set to it, it would have answered here.

This is ARP spoofing, and it takes a few lines of code. Once Eve is in the middle, she can read everything that isn’t encrypted, change it, or quietly drop it. It only works on the local network: Eve has to be on the same Ethernet or Wi-Fi as her victims. But that includes every café, hotel and library network you’ve ever joined.

There are defenses. Business-grade switches can check every ARP message against a list of which address really belongs on which port (“dynamic ARP inspection”). Many Wi-Fi networks stop devices from talking to each other directly at all (“client isolation”), so Eve’s lies never arrive. You can watch your own cache for suspicious changes, which is this chapter’s lab. But the real answer is further up: if everything Bob sends is encrypted, Eve in the middle learns almost nothing. That’s HTTPS, in Chapter 32.

ICMP: the internet’s small talk

When something goes wrong with a packet, the network needs a way to say so. A router that throws a packet away because its hop limit ran out, or because it’s too big, or because it has no route to the destination, sends a short note back to the packet’s sender. The notes are part of the Internet Control Message Protocol, ICMP, which travels inside IP packets (protocol number 1). Every ICMP message starts with a type and a code:

TypeCodeMeansSent by
80echo request: “are you there?”ping
00echo reply: “yes!”the computer being pinged

33port unreachable: “nobody home” (Chapter 12)the destination
34too big, and you said don’t fragment. (It includes the MTU.)a router (Chapter 20)
313forbidden: a firewall said noa firewall, if it’s polite
110time exceeded: the hop limit reached zeroa router (Chapter 11)
50–3redirect: “use that other router instead”a router, rarely

Every error message carries a copy of the start of the packet that caused it: its IP header, and at least the first 8 bytes after that. That’s just enough to include the port numbers of a TCP or UDP packet, so the operating system can tell exactly which program’s packet died:

ICMP messages are never sent about other ICMP errors, or about broadcasts, so that one problem can’t set off a storm of complaints.

How ping works

ping sends an echo request, and the destination’s operating system sends back an echo reply with the same data in it. That’s all. The clever parts are in the details. Each request carries an identifier, so two pings running at once don’t get each other’s replies, and a sequence number, so a missing or late reply can be spotted. And ping puts the time it sent the request into the request’s own data, so it doesn’t have to remember anything: the reply brings the time back with it. Here’s a ping from this chapter’s lab, byte by byte:

$ python3 pyping.py 192.168.1.4 -c 1 -v PING 192.168.1.4 (192.168.1.4): 56 data bytes, hop limit 64 64 bytes from 192.168.1.4: icmp_seq=1 ttl=64 time=27.1 ms sent (ICMP): ⟦1:08 00⟧ e1 98 ⟦2:6e 52 00 01⟧ ⟦3:41 da ae 63 b0 a6 dc ec⟧ 00 01 02 03 04 05 06 07 08 09 0a 0b 0c 0d 0e 0f … received (ICMP): ⟦4:00 00⟧ e9 98 6e 52 00 01 41 da ae 63 b0 a6 dc ec 00 01 02 03 04 05 06 07 08 09 0a 0b 0c 0d 0e 0f … 1 | Type 8, code 0: echo request. Then the checksum (Chapter 10). 2 | The identifier (this program’s number) and the sequence number, 1. 3 | The time it was sent, as 8 bytes. The rest is filler, to make up the size. 4 | Type 0: echo reply. Everything else comes back unchanged, except the checksum, which changes because the type did.

The reply’s ttl is a clue too. Computers start their hop limit at a round number: Linux and macOS at 64, Windows at 128, and many routers at 255. A reply from 1.1.1.1 arriving with 58 has probably come 6 routers from a server that started at 64.

Bob’s friend runs a website on a server at home. Bob pings it, and gets nothing back at all. “Your server’s down!” he says. But his friend can see people using the website. How can both be true?

Many firewalls, and some home routers, simply ignore echo requests, to be less visible to anyone scanning the internet. A server that doesn’t answer pings can be perfectly healthy, and a server that answers pings can have a broken website. ping tests one thing only: whether ICMP gets there and back. Routers use whatever address their outgoing cable has, and nobody outside needs to reach these ones. 3 | Two different routers answered for hop 10. Big networks spread traffic across several equal paths, and each probe can take a different one. (Classic traceroute changes the port number for every probe, which changes the path. A version called Paris traceroute keeps it fixed.) 4 | 26 milliseconds, then 123. That jump is the one hop that crosses an ocean. Chapter 17’s speed of light, spotted in the wild.

The Mac’s traceroute sends UDP packets by default, to ports nobody uses, so the destination answers with “port unreachable”. -I uses pings instead, like Windows’ tracert, which gets through some firewalls that block the UDP kind, and vice versa. The two can even take different paths, because routers that spread traffic across several links choose by looking at the packet. Timings in the middle of a traceroute can mislead, too: a router answers its own ICMP errors slowly, as a low priority job, even when it forwards everyone else’s packets quickly. That’s why mtr, which runs traceroute over and over and keeps statistics, is the tool network engineers actually reach for.

Mike Muuss wrote ping in one evening in December 1983, while chasing a network problem at the US Army’s research laboratory. He named it after the sound of a submarine’s sonar. Van Jacobson wrote traceroute in 1987, using the same trick with the hop limit that we invented in Chapter 11.

ICMP has been misused in some creative ways. In 1996, the “ping of death” crashed many computers with an oversized ping, sent in fragments that added up to more than the 65,535 bytes an IP packet is allowed to have. The “smurf attack” sent pings to whole networks’ broadcast addresses, pretending to be from a victim, who then got thousands of replies at once. As a result, many network administrators block ICMP entirely. That’s a mistake: without “too big” messages, path MTU discovery breaks (Chapter 20), and connections mysteriously hang whenever a large packet is sent. It’s called a “black hole”, and it’s one of Chapter 38’s cases.

What’s next?

Alice’s laptop didn’t choose 192.168.1.7 itself. Something handed it that address when it joined the Wi-Fi, along with the router’s address and more. And every one of these addresses is private: 192.168.1.7 can’t travel across the internet at all. So how did Bob’s pings reach 1.1.1.1, and how did the replies find their way back? Chapter 22 opens up the home router.

Experiments

  • Run python3 pyping.py 1.1.1.1 --ttl N for N from 1 to 8. You’ve just done a traceroute by hand. Which hops don’t answer?
  • Traceroute to a server on another continent with pytrace.py. Find the hop where the time jumps. Use Chapter 17’s lightspeed.py to work out how far that jump would take light in fiber.
  • Add a --udp mode to pytrace.py: send UDP datagrams to port 33434 and up, and wait for “time exceeded” or “port unreachable”. Do you get a different path? (On Linux, use the error queue on the UDP socket. On a Mac, keep the ICMP socket open to hear the answers.)
  • Ping the same computer on your network twice, a few seconds apart, and watch its ARP entry with ip neigh (or arp -an) in between. On Linux, can you catch it in the DELAY or PROBE state?
