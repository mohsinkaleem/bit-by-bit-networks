Grandpa’s garden is slow

Grandpa Otto’s garden website is a success. His neighbours visit it, his friends from the allotment visit it, and his daughter visits it every morning to see the photos of the beans. And every morning, it takes ages to load.

B: It’s just one page and some photos, served from the Pi. How can it be slow? A: Open your browser’s developer tools. The Network tab. Now reload. B: It downloaded every photo again. Two and a half megabytes each. They haven’t changed since yesterday! A: Because the Pi never told the browser it could keep them. And look at the timings: it opened a new connection for each one. B: So the web isn’t just “ask for a page, get a page”? A: That was Chapter 6. Real HTTP has thirty years of tricks for doing less work: keep the connection open, don’t send what they already have, squash what you do send. Grandpa’s Pi uses none of them.

In Chapters 6 and 7, Alice and Bob invented the web: requests and responses, headers, status codes, forms, cookies and chunked replies. The real protocol, HTTP/1.1, is exactly that, with much more learned along the way. This chapter goes through the parts that matter most in real life: connections that stay open, caching, compression, redirects, fetching part of a file, cookies done safely, and the JSON APIs that apps use to talk to servers. (Most big websites now use HTTP/2 or HTTP/3 instead, which carry the very same requests and headers in a more efficient way: that’s Chapter 33.)

Keep the line open

In the original HTTP, every request needed a new TCP connection: connect, ask, receive, hang up. A web page with a picture on it meant two connections, each with its own handshake. Today a page loads dozens or hundreds of files, and over HTTPS each new connection needs a TCP handshake and a TLS handshake before the first request can even be sent. So HTTP/1.1 keeps connections open by default, and sends request after request over the same one:

Keeping a connection open only works if each side can tell exactly where a message ends, which is why every response needs a Content-Length, or Transfer-Encoding: chunked (Chapter 7) when the server doesn’t know the length in advance. Our Chapter 6 server just closed the connection to say “that’s all”, which is what info.cern.ch still does. This chapter’s lab handles all three:

HTTP/1.1 has a weakness here, though: on one connection, responses must come back in the order the requests were sent. A slow response holds up everything behind it. (The standard allowed sending several requests without waiting, called “pipelining”, but so many servers and proxies got it wrong that browsers never switched it on.) So browsers open up to six connections to each server at once, and use them in parallel. Chapter 33’s HTTP/2 fixes this properly.

Don’t send it again: caching

The fastest request is the one you don’t make. Every browser keeps a cache of what it has downloaded, and the server’s response headers say what it may do with it:

  • Cache-Control: max-age=86400: this is fresh for a day. Until then, use your copy without asking.
  • Cache-Control: no-cache: keep it, but check with me every time before using it. (A confusing name: it doesn’t mean “don’t cache”.)
  • Cache-Control: no-store: this does mean don’t keep it: for pages with bank balances or medical records.
  • Cache-Control: private: your browser may keep this, but shared caches (like a company’s proxy, or a CDN) mustn’t.

When a cached copy stops being fresh, it isn’t thrown away. The browser asks the server whether it has changed, by sending back the validators it was given: If-None-Match with the ETag, or If-Modified-Since with the date. If nothing has changed, the server answers 304 Not Modified, with no body at all:

$ python3 httpclient.py cache http://info.cern.ch/ first request: 200, 646 bytes; ETag "286-4f1aadb3105c0", Last-Modified Wed, 05 Feb 2014 16:00:31 GMT asking again with If-None-Match, If-Modified-Since: second request: ⟦1:304, 0 bytes⟧ → “not modified”: use the copy you have 1 | For a 646-byte page that hardly matters. For Grandpa’s 2.4 MB photos, it’s the difference between an instant page and a slow one.

Notice the trade-off. With a long max-age, the page is instant, and the server does no work at all, but when Grandpa uploads a new photo, visitors keep seeing the old one until their copy expires. Websites get the best of both with a trick: they put a fingerprint of each file’s contents into its name (beans.3f9a1c.jpg), cache it for a year, and when the file changes, the page simply refers to a new name.

Caches aren’t only in browsers. Big websites put shared caches between themselves and their visitors, all over the world: that’s what a content delivery network is (Chapter 34). You can often see them in the headers:

$ curl -sI --http1.1 https://example.org | grep -iE "^HTTP|cache|age|last-mod|server" HTTP/1.1 200 OK Server: cloudflare last-modified: Sat, 26 Sep 2026 09:09:07 GMT ⟦1:Age: 12846⟧ ⟦2:Cache-Control: max-age=14400⟧ ⟦3:cf-cache-status: HIT⟧ 1 | This copy has been sitting in the shared cache for 12,846 seconds, about three and a half hours… 2 | …out of the four hours it may be kept. After that, the cache will check with the real server. 3 | Cloudflare’s own header: this answer came from its cache, and the real server never heard about the request.

Smaller on the wire

Text squashes well: web pages are full of repeated words and tags. So browsers say which compression methods they understand, and servers compress the response with one of them:

$ python3 httpclient.py gzip https://en.wikipedia.org/wiki/Hypertext_Transfer_Protocol Accept-Encoding: identity → HTTP/1.1 200 OK, Content-Encoding: none 612,715 bytes on the wire Accept-Encoding: gzip → HTTP/1.1 200 OK, Content-Encoding: ⟦1:gzip⟧ ⟦2:100,735 bytes on the wire⟧ 1 | gzip is the same method as the gzip command, from 1992. Browsers also offer br (Brotli) and zstd, which squeeze a little harder. 2 | Six times smaller. Photos and videos are already compressed, so they don’t shrink, and servers don’t bother trying.

A response that depends on the request’s headers must say so, with Vary: Accept-Encoding, or a shared cache might hand a compressed copy to a browser that asked for an uncompressed one.

Go over there: redirects

A response with a status code in the 300s and a Location header tells the browser to ask somewhere else instead. 301 and 308 mean “moved for good: remember the new address”; 302 and 307 mean “over there, for now”. (The difference within each pair is whether the browser may change a POST into a GET on the way, for historical reasons.) Almost every website uses a couple:

That last header matters more than it looks. Remember Eve in Chapter 21, sitting in the middle of Bob’s Wi-Fi with a forged ARP answer? The very first, unencrypted http:// request is her chance: she can answer it herself, and never redirect Bob to the real, encrypted site at all. Strict-Transport-Security takes that chance away, at least after the first visit, and the preload means the BBC has asked browser makers to build it into the browser, so there’s never a first unprotected visit. Chapter 32 explains why HTTPS defeats Eve completely.

Just part of it: ranges

Accept-Ranges: bytes in info.cern.ch’s response means a client can ask for just part of the file:

$ python3 httpclient.py range http://info.cern.ch/ 0-99 ⟦1:206⟧, Content-Range: ⟦2:bytes 0-99/646⟧, got 100 bytes:
http://info.cern.ch

http://info.cern 1 | 206 Partial Content. 2 | The first 100 bytes, of 646.

That’s how a download that was interrupted can carry on where it stopped, and how a video player can jump to the middle of a film without downloading the beginning.

Cookies, done properly

In Chapter 7, Bob’s server gave each visitor a cookie so that it could recognise them next time. The real Set-Cookie header has grown a list of attributes, most of them about keeping cookies from being stolen:

A cookie that proves you’re logged in is as good as your password, for as long as it lasts, so these attributes matter. Secure keeps it off unencrypted connections, where Eve could read it. HttpOnly keeps it away from any script that sneaks into the page. And SameSite stops other websites from making your browser send requests that carry it: without it, a web page could contain a hidden form that posts to your bank, and your browser would helpfully attach your bank’s cookie. Browsers have also started blocking “third-party” cookies, set by a different site from the one you’re visiting (usually an advertising network, which used them to follow people from site to site).

Talking to programs: JSON APIs

Most HTTP requests today aren’t from a person clicking a link. They’re from an app, asking a server for data: the weather, your messages, the next ten videos. These APIs use HTTP exactly as a browser does, but the bodies are usually JSON, a text format for numbers, strings, lists and dictionaries that every programming language can read. Grandpa wants to know whether to water his beans:

$ python3 api.py weather GET https://api.open-meteo.com/v1/forecast?latitude=51.5&longitude=-0.12¤t=temperature_2m,precipitation&daily=precipitation_sum&forecast_days=3&timezone=Europe%2FLondon → 200 OK, Content-Type: application/json; charset=utf-8 in the garden now: 18.1 °C, 0.0 mm of rain 2026-09-28: 0.0 mm of rain (water the beans!) 2026-09-29: 1.4 mm of rain 2026-09-30: 4.4 mm of rain

APIs use HTTP’s methods to say what kind of thing is being done: GET to read, POST to create, PUT or PATCH to change, DELETE to remove. The difference matters to everything in between: a GET must be safe (it changes nothing, so a cache may answer it, and a browser may repeat it), and a PUT or DELETE must be idempotent (doing it twice has the same effect as doing it once, so it can be retried if the answer is lost). The lab has a tiny API for Grandpa’s plants, and a client that tries each method:

$ python3 api.py demo GET /plants → 200 [{"id": 1, "name": "runner beans", "planted": "2026-05-02"}] POST /plants → ⟦1:201⟧ Location: /plants/2 {"id": 2, "name": "courgettes", "planted": "2026-06-01"} GET /plants/2 → 200 {"id": 2, "name": "courgettes", "planted": "2026-06-01"} POST /plants → ⟦2:400⟧ {"error": "send JSON with a name"} DELETE /plants/1 → ⟦3:204⟧ (no body) DELETE /plants/1 → 204 (no body) GET /plants/1 → 404 {"error": "no plant 1"} GET /plants → 200 [{"id": 2, "name": "courgettes", "planted": "2026-06-01"}] 1 | 201 Created, with the address of the new thing in Location. 2 | 400 Bad Request: the request itself was wrong. Status codes in the 400s blame the client; in the 500s, the server. 3 | 204 No Content: done, and nothing to say. Deleting it again gives the same answer: idempotent.

A web page on garden.example uses JavaScript to fetch data from Grandpa’s API on api.garden.example, and the browser refuses to let the script read the answer. Why would a browser block a request the page asked for?

Because of the same-origin policy: a script from one site may not read responses from another, or any website could quietly read your email from your webmail’s API, using your cookies. A different name counts as a different site. The API has to opt in, by answering with a header like Access-Control-Allow-Origin: https://garden.example, a system called CORS (cross-origin resource sharing). For some requests, the browser even asks first, with an OPTIONS request, before sending the real one. It confuses every web developer the first time: the request usually arrives, and it’s the browser, not the network, that hides the answer.

HTTP/1.1 was first published in 1997, revised in 1999, and completely rewritten, with the same meaning but much clearer wording, in 2014 and again in 2022, when the parts shared by every version of HTTP (methods, status codes, headers, caching) were separated from how HTTP/1.1 writes them on the wire. One of its main authors, Roy Fielding, described the ideas behind its design in his PhD thesis in 2000, and gave them a name that stuck: REST, which is why APIs like Grandpa’s are often called “RESTful”.

The Host header was one of 1.1’s most important additions. Before it, every website needed its own IP address, which would have made the address shortage (Chapter 25) far worse.
