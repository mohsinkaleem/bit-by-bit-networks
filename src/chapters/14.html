Numbers are for computers

Alice keeps a page at the back of her notebook: Grandpa Otto is 4.2, the library catalog is 3.1, the school newsletter is 2.7. It works, mostly. But she has to copy the list onto every computer she uses, she keeps mistyping 2.7 as 7.2, and when the library gets a second computer she has no idea it exists.

People are good at names and bad at numbers. Computers are the other way round. So let’s give every computer a name as well as a number, and teach the network to translate one into the other. It sounds like a small convenience, but doing it well, for a whole town and eventually the whole world, is a surprisingly deep problem.

Everyone keeps a list

The simplest plan is for every computer to keep its own list of names and numbers, and look names up in it. When Alice types otto, her computer looks in its list, finds 4.2, and sends the packets there.

It’s fine for a handful of computers. But every time a computer is added, renamed or renumbered, somebody has to update every list in town, and in the meantime the lists disagree. And who decides what the names are? If Otto and a boy at school both want to be called otto, whose list wins?

One big phone book

Better: keep one list, on one computer, and let everyone ask it. When Alice’s computer needs Otto’s number, it sends a question to the name server: “what’s the number for otto?”, and gets back “4.2”. Now there’s only one list to update, and one place that decides who gets which name.

That’s a big improvement, and it fixes the town for a while. But look at what happens as the town grows:

  • Every question from every computer goes to the same place, so the name server gets busier and busier.
  • If it breaks, nobody can find anybody, even though the network itself is fine.
  • Every new name, from every school, library and house in town, has to be added by whoever looks after that one computer. They become a bottleneck, and a very powerful person.

We’ve seen this shape of problem before. In Chapter 11, one flat list of card addresses didn’t scale, and the fix was to give addresses parts: a network part and a host part. Let’s do the same for names.

Names with parts

We give every name a family name. Otto’s computer is otto.seaside, the school newsletter is newsletter.school, and Alice is alice.street. Now the names form a tree:

Here’s the clever part: each piece of the tree is looked after by whoever owns it. The town looks after the very top, called the root, but all it keeps is a short list saying who is in charge of each second part: “for anything ending in .seaside, ask Otto’s town’s name server”. Otto’s town runs that name server itself, and can add harbor.seaside or cafe.seaside whenever it likes, without asking anybody. Handing over a piece of the tree like this is called delegation.

Nobody has to know every name any more. Each name server only knows its own little part, plus where to find the parts below it.

Asking around

Finding a name now takes several questions: first the root, then whoever the root points to, and so on. Alice’s computer could do all that asking itself, but instead each street runs a helpful name server whose job is to do the asking for everyone. It’s called a resolver, and every computer on the street is told its address when it joins the network.

Step 5 is what makes the whole system work. Most answers come straight out of the resolver’s memory, so the root and the other name servers only hear a tiny fraction of the questions people ask.

Remembering, and forgetting

Every answer comes with a “good for” time, chosen by its owner. Otto’s town says otto.seaside is 4.2, good for one hour. The root says “ask seaside’s server”, good for two days, because that almost never changes. The resolver remembers each answer until its time runs out, then forgets it. This is called caching, and the “good for” time is its time to live, or TTL (the same idea, and the same name, as the hop limit from Chapter 11).

If Otto moves while resolvers still remember his old number, people will be sent to the wrong place until those memories expire. The owner of a name has to pick a balance: long TTLs mean fewer questions and faster answers, short TTLs mean changes spread quickly. A good trick, if you know a move is coming, is to shorten the TTL a day or two before you move.

More than addresses

Once there’s a system for looking things up by name, it turns out to be useful for more than addresses. Each entry in a name server is a record, and there are several kinds:

KindMeansExample
Athis name’s addressotto.seaside → 4.2
NSthe name server in charge of this part of the treeseaside → seaside’s server
MXwhere to deliver mail for this nameseaside → post.seaside
CNAMEthis name is just another name for that onenews.school → newsletter.school
TXTany bit of text the owner wants to publish“mail from seaside only comes from post.seaside”

Can you believe the answer?

Every question sent to a name server is just a datagram, and so is every answer. There’s no connection, no handshake, nothing to prove where the answer came from. Resolvers match an answer to their question by a question number. So Eve has an opening:

This is called cache poisoning, and it’s nasty: one successful fake answer misleads everyone on the street for as long as the TTL Eve chose. The defenses are all about making Eve guess:

  • Pick a random question number each time, not 1, 2, 3…
  • Send each question from a random port (Chapter 12). Eve now has to guess the port too.
  • Only accept an answer that comes from the server you actually asked.

With 65,536 possible question numbers and tens of thousands of possible ports, Eve has to guess right among billions of combinations, in the fraction of a second before the real answer arrives. In the lab you’ll watch her succeed against a naive resolver and fail against a careful one. The complete fix is for name servers to sign their answers, so that forgeries can be detected, but that needs the cryptography of Part II.

The real system is the Domain Name System, DNS, invented by Paul Mockapetris in 1983. Before it, the whole internet really did use one list: a file called HOSTS.TXT, kept by the Network Information Center at Stanford Research Institute. Every computer downloaded a fresh copy now and then, and to add a name you phoned or emailed the NIC. By the early 1980s the file was changing faster than people could download it.

Real names are read right to left, just like ours. In www.example.com, the root delegates com to one organization, which delegates example.com to whoever registered it, who can then create www.example.com or anything else ending in .example.com. There are 13 root server names, from a.root-servers.net to m.root-servers.net, run by 12 different organizations, but each name is really hundreds of machines spread around the world, all answering to the same address (a trick called anycast). Name servers listen on port 53, over UDP for ordinary questions and TCP for big answers.

Your computer’s resolver is usually your home router, which passes questions on to your internet provider’s resolvers. Some people use public ones instead, like Cloudflare’s 1.1.1.1 or Google’s 8.8.8.8. And the list-on-every-computer idea never died: every computer still has a small one, in /etc/hosts, which it checks first.

In 2008, Dan Kaminsky found a way to make cache poisoning dramatically faster, and the world’s DNS software was quietly updated in a coordinated effort before he revealed it. The main fix was random ports for questions. Signed answers, called DNSSEC, are Chapter 29’s story.

Names ending in .local work differently. There’s no name server at all: your computer broadcasts the question to your own network, like Chapter 11’s “who has?”, and the computer with that name answers for itself. This is multicast DNS, and it’s how ssh raspberrypi.local finds a Raspberry Pi with no setup at all.

What’s next?

Look back at how far we’ve come. We started with a flashlight in a bedroom window, and now Alice can type otto.seaside into a program and send her grandpa a fifty-page report, reliably, across a town of networks, through routers that work out the routes for themselves, with every bit checked on the way.

Along the way, we invented a lot of things and gave them names. The real internet invented the same things, and gave them different names. In the last chapter of Part I, we’ll line them all up, and then follow one real message through every layer, using the tools on your own computer.

names.py runs the town’s whole naming system on your computer: a root server, a name server for each part of town, and a resolver, all using real UDP datagrams. lookup.py asks questions, and eve.py tries to cause trouble. You’ll need two or three terminals.

1. Start the name servers

$ cd labs/ch14 $ python3 names.py root name server on port 7053: seaside, school, library, street seaside name server on port 7054: otto.seaside, harbor.seaside, cafe.seaside school name server on port 7055: newsletter.school, teacher.school library name server on port 7056: catalog.library street name server on port 7057: alice.street, bob.street, carol.street resolver on port 7050 Ready. Ctrl-C to stop.

4. Otto moves

$ python3 lookup.py otto.seaside otto.seaside is 4.2 (fresh, good for 30s; answered in 1.0 ms) … $ python3 lookup.py --update otto.seaside 4.9 told the seaside name server: otto.seaside is now 4.9 $ python3 lookup.py otto.seaside otto.seaside is 4.2 (remembered, 29s left; answered in 0.6 ms) $ python3 lookup.py otto.seaside --trace | tail -1 2. port 7054 says: otto.seaside is 4.9 (good for 30 seconds)

The resolver is confidently wrong. Seaside’s server knows the new number, but the resolver won’t ask again until its memory expires. Wait 30 seconds and try again.

5. Eve poisons the resolver

Stop names.py and restart it with --naive. The naive resolver numbers its questions 1, 2, 3…, always asks from port 7051, and believes any answer with the right number. Start Eve, and within a few seconds, look up a name the resolver hasn’t seen yet:

$ python3 names.py --naive $ python3 eve.py harbor.seaside 6.66 Eve is sending fake answers “harbor.seaside is 6.66” to port 7051 for 10 seconds... $ python3 lookup.py harbor.seaside harbor.seaside is 6.66 (fresh, good for 3600s; answered in 1.1 ms) the resolver asked root (port 7053) about harbor.seaside $ python3 lookup.py harbor.seaside harbor.seaside is 6.66 (remembered, 3600s left; answered in 0.8 ms)

The Field Guide takes a real dig +trace apart line by line: the root, then the com servers, then example.com’s own servers, just like otto.seaside. It also shows how to see which resolver your computer uses, and how .local names are found.

Experiments

  • Add a new part of town, moon, with its own name server on port 7058 and a couple of names. What do you have to change in the root’s zone?
  • Add an alias record kind: ("C", "newsletter.school", 30) for news.school, and teach the resolver to follow it.
  • Make eve.py guess random question numbers from 0 to 65,535 instead of 1 to 49, against the naive resolver. How long does she need now?
  • Look up your own computer’s name with dscacheutil -q host -a name $(hostname) on a Mac, or getent hosts $(hostname) on Linux. Where did the answer come from?
