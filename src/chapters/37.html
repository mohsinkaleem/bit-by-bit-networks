Grandpa’s question

It’s Sunday, and the family is round at Grandpa Otto’s. He has been reading Bob’s notebooks.

G: I type the name of my garden website, I press Enter, and there it is. What actually happens? B: Where do I start? There’s DNS, and TCP, and TLS… A: Start at the beginning, and don’t skip anything. We’ll record the whole thing on the Pi, and go through it packet by packet. G: How long will that take? A: For the Pi? About a fifth of a second. For us, one chapter.

“What happens when you type a URL and press Enter?” is a famous interview question, because a complete answer touches every layer of networking. That’s this chapter: one page, https://example.org/, fetched from Grandpa’s Pi, with every step pointing back to the chapter that explained it. Here’s the route we’ll take:

Before the first packet

A browser does a surprising amount of work before it sends anything. It decides whether you typed an address or a search. It adds https://, and checks its HSTS list (Chapter 30) in case the site insists on it. Then it looks for shortcuts, because the fastest network request is the one you don’t make:

  • Is the page in the HTTP cache, and still fresh (Chapter 30)? Then there’s nothing more to do.
  • Is there already an open connection to this site (Chapters 30 and 33)? Then skip straight to sending the request.
  • Is the address in the DNS cache, the browser’s own or the operating system’s (Chapter 29)? Then skip the lookup.
  • Did the site once say Alt-Svc: h3, or does its DNS have an HTTPS record (Chapter 33)? Then try QUIC.

For this chapter we’ll assume none of the shortcuts work, and use curl on the Pi, with its ARP cache emptied first, so that every step happens for real. The capture was decrypted with curl’s SSLKEYLOGFILE (Chapter 32), so we can see inside everything.

Which way is out?

The Pi’s routing table (Chapter 20) says that anything not on the home network goes to the default route: the router, 192.168.1.1, on wlan0. DHCP set that up when the Pi joined the network (Chapter 22), along with which DNS server to use: the router again. But a packet on Wi-Fi needs the router’s MAC address, and the cache is empty, so the very first packet isn’t about example.org at all:

Across the internet

Now the Pi knows where to go: 172.66.157.237. Every packet from here on goes first to the router, which rewrites its source address to the house’s public one (NAT, Chapter 22), then along the internet provider’s PPPoE line (which is why nothing bigger than 1,492 bytes gets through, Chapter 27), and from router to router, each looking up the longest matching prefix in its table (Chapters 20 and 23). Which network carries it where is settled by BGP, the treaty between thousands of networks (Chapter 24). And because Cloudflare announces example.org’s addresses from hundreds of cities at once, the packets end up at the nearest one (anycast, Chapter 34), a few milliseconds away.

One packet, every layer

Take just one of those packets, number 23, the request. It carries a whole stack of the protocols in this book, each wrapped inside the one below, and each read by a different machine on the way:

The Wi-Fi header gets it to the router, which throws it away and writes a new one for the next link. The IP header gets it across the internet, rewritten by NAT on the way. The TCP header gets it to the right program, in the right order, at the right speed. The TLS record keeps everything inside it secret and unchanged. And inside all that, 28 bytes of compressed headers that say, in effect, what Grandpa typed.

And then the page

The 713 bytes of example.org are one tiny page, which came back in a single round trip. Most pages are nothing like that. The browser reads the HTML, and finds the stylesheets, scripts, fonts and pictures it refers to, often dozens of them, from a dozen different sites. Files on the same site go over the same HTTP/2 connection, all at once. Each other site needs its own DNS lookup, handshakes and all, which is why pages that load things from many sites are slow, and why browsers start those lookups and connections the moment they see a name mentioned. For a big download, what matters is no longer the round trips but the bandwidth, and how quickly TCP’s congestion control (Chapter 28) finds it: a long Wikipedia article spends most of its time there.

That was the slowest possible way to fetch example.org: nothing cached, nothing reused. If Grandpa reloads the page a minute later, in a real browser, which of those nearly forty packets still need to happen?

Possibly none. The router’s MAC address is in the ARP cache for a while (Chapter 21); the addresses are in the DNS cache for their TTL (Chapter 29); the browser keeps the connection open, so there’s no TCP or TLS handshake (Chapter 30); and if the page is still fresh in the HTTP cache, there’s no request either. Even when a new connection is needed, TLS session tickets skip most of the handshake, and QUIC with 0-RTT (Chapter 33) can send the request in the very first packet. Most of the engineering in this book is about making the second visit cheaper than the first.

“What happens when you type google.com into your browser and press Enter?” is asked in so many job interviews that people have written book-length answers, including a famous community-written one on GitHub that starts with the electrical signal from the keyboard. Even so, the typical page today is far busier than example.org: the HTTP Archive, which regularly loads millions of websites and records what they do, finds that a median page makes around seventy requests, to many different sites, and weighs a couple of megabytes.

What’s next?

Nearly forty packets, eight kinds of protocol, a dozen machines, and it all worked, in less time than it takes to blink. But every step in this chapter is something that can go wrong: a missing route, a wrong DNS answer, a blocked port, a packet too big for a tunnel, a certificate that doesn’t match. Chapter 38, the last in Part II, is about what to do when it breaks: how to find out which step failed, with the tools from this book.

Experiments

  • Fetch the same page with curl --http3-only while capturing (Chapter 33). How many packets does it take now, and how much sooner does the request go out?
  • Add a timing for each DNS question in pressenter.py against 1.1.1.1 instead of your router. Which is faster, the first time and the second?
