Three hundred switches

A few years have gone by. Alice finished her degree and now works full-time on the university’s network team, at the desk next to Carol’s. Bob is a student there himself, and it’s exam week.

C: Tomorrow at nine, the exam halls lose the internet. Only the exam server is allowed, until noon. Then everything goes back. A: How many switches is that? C: Three hundred and twelve. Last year two of us logged into them one by one, all night, pasting settings from a spreadsheet. We missed one. A student in Hall C found the internet, and it was in the newspaper. B: Can’t the switches just be told the rule once? “Exam halls: only the exam server.” C: Every switch has its own brain, and every brain has to be told separately. That’s how networks have worked since before you were born. A: Unless you take the brains out. One program decides, and the switches just do what it says. C: I’ve heard that before. It’s called software-defined networking. The last company that said it sold us a box that needed its own engineer. A: Then let’s build a small one ourselves, and see.

Part III is about where networking is going. Some of it is already here, quietly running in data centres and phones; some of it is still being argued about. This first chapter is about making networks programmable: writing the rules as software, in one place, instead of typing them into boxes one at a time. We’ll build a controller that runs real switches, and then go one step further, and put our own programs inside the Linux kernel.

Brains and hands

Every router and switch in this book has had two jobs. One is deciding: running Chapter 23’s OSPF, or Chapter 24’s BGP, or Chapter 9’s address learning, to work out where things should go. The other is doing: taking each packet as it arrives, looking it up, and sending it on its way, millions of times a second. Engineers call them the control plane and the data plane.

In a traditional network, both live in every box, and every box is set up separately, by a person with a login and a lot of patience. Software-defined networking (SDN) separates them. The switches keep the data plane: a table of rules, and the hardware to follow them very fast. The control plane moves into an ordinary program on an ordinary server, the controller, which sees the whole network at once and writes the switches’ rules for them. Carol’s exam rule becomes one line in one program, sent to 312 switches in a second.

OpenFlow: a table you can write to

For a controller to write a switch’s rules, they need a shared language. The first widely used one was OpenFlow, from 2008. An OpenFlow switch has a flow table: a list of rules, each with a priority, a match (which packets it applies to) and actions (what to do with them). A packet is checked against the rules from the highest priority down, and the first one that matches wins, just like Chapter 34’s firewall rules. The matches can use almost any header field from Part II: the port it came in on, Ethernet addresses, VLAN, IP addresses, protocol, TCP and UDP ports. The actions include “send it out of port 2”, “flood it everywhere”, “change this field”, and “send it to the controller”. A rule with no actions means: drop it.

Switch and controller talk over an ordinary TCP connection, usually to port 6653. Every message starts with the same eight bytes:

version | 1 byte: 4 means OpenFlow 1.3 type | 1 byte: HELLO, FEATURES_REQUEST, PACKET_IN, FLOW_MOD, PACKET_OUT… length | 2 bytes, the whole message id | 4 bytes, to match replies to requests body | depends on the type

What happens when a packet arrives that no rule matches? Usually, the controller installs one rule at the start that matches everything, at the lowest priority: “if nothing else matches, send it to me”. Then the first packet of every new conversation goes to the controller, which decides what to do and teaches the switch:

The controller is now a single point of failure. What happens to the network if it crashes?

Less than you might fear. The rules already in the switches keep working, because forwarding never involved the controller. Here’s the lab with the controller stopped altogether:

$ sudo ./sdn_box.sh test h1 → 10.39.0.2 3 packets transmitted, 3 received, 0% packet loss, time 406ms h1 → 10.39.0.3 3 packets transmitted, 0 received, 100% packet loss, time 405ms

h1 and h2 still talk, and h3 is still blocked. What stops working is everything new: a new host, a new conversation once the old rule has timed out, a change of policy. So real controllers run as a cluster of three or five copies that share their view of the network, and take over from each other (with a vote, much like Chapter 24’s treaties need everyone to agree). A switch can also be told to fall back to ordinary learning-switch behaviour if it loses its controller: that’s fail-mode=standalone, Open vSwitch’s default.

P4: teach the switch new protocols

OpenFlow lets you fill in a switch’s tables, but not choose what the tables look like: the switch’s makers decided which header fields it can read. When a new protocol appears (Chapter 35’s VXLAN, say), OpenFlow switches can’t match on it until the OpenFlow standard, and then the switch chips, catch up. That took years, and OpenFlow’s list of fields kept growing.

P4, from 2014, turned that around. It’s a programming language for the data plane itself. A P4 program describes the whole pipeline a packet goes through: how to parse the headers (Ethernet, then IPv4, then UDP, then… whatever you invent), which tables to look up and what actions they can take, and how to put the packet back together:

Here is a small piece of a P4 program: a table that does Chapter 23’s longest-prefix match on the IPv4 destination, and an action that forwards a packet the way a router does (Chapter 20: new Ethernet addresses, one less time-to-live):

P4: part of a simple IPv4 router (a sketch; not run in this book)
action forward(macAddr_t next_hop, egressSpec_t port) {
    standard_metadata.egress_spec = port;
    hdr.ethernet.srcAddr = hdr.ethernet.dstAddr;
    hdr.ethernet.dstAddr = next_hop;
    hdr.ipv4.ttl = hdr.ipv4.ttl - 1;
}

table ipv4_lpm {
    key = { hdr.ipv4.dstAddr: lpm; }
    actions = { forward; drop; }
    size = 1024;
}

A P4 compiler turns programs like this into the settings of a special switch chip, whose parser and tables can be rearranged, while still forwarding billions of packets per second. The entries in ipv4_lpm are filled in at run time by a controller. It also makes things possible that no fixed switch could do, like in-band network telemetry: each switch stamps a packet with how long it waited in the queue there, so the receiver gets a hop-by-hop timing report inside the packet itself, a traceroute that costs nothing.

eBPF: programs inside the kernel

Meanwhile, at Grandpa Otto’s, the Pi has a problem of its own. Something on the neighbour’s network (a smart plug, Bob suspects) has taken to pinging it several times a second, all day. It’s harmless, but it’s annoying, and Grandpa wants it stopped “at the door”.

A firewall rule would do (Chapter 34), but there’s a more interesting way, and it’s the way the biggest networks in the world now protect themselves. Remember Chapter 16’s packet filters: tiny programs, compiled by tcpdump and run by the kernel on every packet, to decide which ones to capture. Linux grew that idea into eBPF (extended BPF): a way to load small programs of your own into the running kernel, safely, and attach them to hooks, places where the kernel calls them. For networking, the most important hooks are on the packet’s way in:

The earliest hook, XDP (the “express data path”), runs a program on each frame straight out of the network card’s driver, before Linux has spent any effort on it. A program there can drop a packet, send it back out, pass it on up, or even rewrite it into something else. That’s why it’s used to fight floods of attack traffic, and to build load balancers (Chapter 34) that handle millions of packets per second per server.

Why doesn’t this crash the kernel? Because every program passes through the verifier before it’s allowed to run. The verifier explores every path through the program, and refuses it unless it can prove the program always finishes, never reads memory it shouldn’t, and never reads past the end of a packet. Programs that pass are then compiled into the processor’s own machine code (“just in time”, JIT), so they run at full speed. And programs keep their results in maps, pieces of memory that ordinary programs can read too.

Writing eBPF by hand

Normally people write eBPF programs in C, or Rust, or through tools that generate them. This chapter’s ebpf.py does it the hard way, and the clearest: it assembles the instructions itself, and hands them to the kernel with the bpf() system call, using nothing but Python’s standard library. Each instruction is eight bytes:

The first program counts packets and bytes for each IP protocol. It reads the Ethernet type at offset 12 and the IP protocol at offset 23, exactly as Chapter 16’s tcpdump filter did, then adds to a counter in a map:

$ sudo python3 ebpf.py count wlan0 5 loaded “count”: 17 instructions, passed the verifier, compiled to ⟦1:264 bytes of aarch64 machine code⟧ (program id 100) counting IPv4 packets on wlan0, in the kernel, for 5 s: 1 s ICMP 4 (0.4 kB) TCP 1 (0.1 kB) UDP 4 (0.4 kB) 2 s ICMP 8 (0.8 kB) ⟦2:TCP 32 (10.6 kB)⟧ UDP 6 (0.6 kB) 3 s ICMP 12 (1.2 kB) TCP 32 (10.6 kB) UDP 6 (0.6 kB) 4 s ICMP 14 (1.4 kB) TCP 32 (10.6 kB) UDP 6 (0.6 kB) 5 s ICMP 14 (1.4 kB) TCP 36 (11.0 kB) UDP 6 (0.6 kB) 1 | Our 17 instructions, compiled by the kernel into real ARM processor instructions, 66 of them (they’re 4 bytes each). 2 | Meanwhile the Pi was pinging 1.1.1.1, looking up a name and fetching https://example.org/: the page and its TLS handshake arrived in the second second. The counting happened in the kernel; Python only read the map, once a second.

The second program is Grandpa’s doorman. It runs at the XDP hook, and drops ICMP echo requests (pings), letting everything else through. Notice the first check: before it reads any byte of the packet, it must prove the packet is long enough. That’s not good manners; the verifier won’t accept the program without it.

The kernel says no

What if Bob forgets a check? ebpf.py verifier tries two broken programs: the counter without checking that the map lookup succeeded, and the doorman without checking the packet’s length.

$ sudo python3 ebpf.py verifier “no_null_check”: the verifier said no (Permission denied): … 12: (db) lock *(u64 *)(r0 +0) += r1 … ⟦1:R0 invalid mem access 'map_value_or_null'⟧ “no_bounds_check”: the verifier said no (Permission denied): … invalid access to packet, off=12 size=2, R2(id=0,off=12,r=0) … ⟦2:R2 offset is outside of the packet⟧ 1 | The map lookup returns either a pointer or zero, and the verifier tracked that through every instruction. At instruction 12 we add to whatever r0 points at, and r0 might be zero. In a C program that would crash the kernel; here it never runs. 2 | The doorman reads 2 bytes at offset 12 of the frame without first proving the frame has at least 14 bytes. r=0 means: so far, zero bytes are known to be safe.

That’s the bargain eBPF offers: you can run your own code in the most sensitive place in the computer, as long as you can convince a very suspicious checker that it’s safe. It’s what makes eBPF different from loading a kernel module, which can do anything, including crash everything.

Asking the kernel questions

eBPF isn’t only for packets. Programs can be attached to thousands of other places in the kernel, which makes it a superb way to answer questions about what a computer is doing. The tool bpftrace turns one-line scripts into eBPF programs. This one watches, across the whole computer, every TCP connection that’s opened, and by which program:

$ sudo bpftrace -e 'tracepoint:sock:inet_sock_set_state /args->protocol == 6 && args->newstate == 2/ { printf("%-8s pid %-6d opens a connection to %s port %d\n", comm, pid, ntop(args->daddr), args->dport); }' Attaching 1 probe... curl pid 12391 opens a connection to 172.66.157.237 port 443 python3 pid 12393 opens a connection to 1.1.1.1 port 80 dig pid 12394 opens a connection to ⟦1:8.8.8.8 port 53⟧ 1 | newstate == 2 is TCP’s SYN_SENT (Chapter 27): the moment a program’s SYN goes out. Even dig +tcp is caught. No program had to be changed, and nothing had to be restarted.

OpenFlow came out of Stanford, where Nick McKeown’s group wanted to try new ideas on real campus networks without buying new hardware; their 2008 paper was called “OpenFlow: Enabling Innovation in Campus Networks”, which is exactly Carol’s situation. One of the students involved, Martin Casado, co-founded Nicira, which built network virtualisation on Open vSwitch and was bought by VMware in 2012 for over a billion dollars. Google described in 2013 how it ran B4, the private network between its data centres, with centralised SDN control, keeping its long-distance links far busier than traditional routing allows.

P4 was designed by several of the same people. It was most famously compiled onto Barefoot Networks’ Tofino switch chips, bought by Intel, which stopped developing new versions in 2023; the language lives on, in network cards and research. eBPF is everywhere: Kubernetes networks (Chapter 36) built with Cilium use it instead of iptables, Meta’s load balancer Katran is an XDP program, and Cloudflare drops attack traffic with XDP before it touches the rest of its servers. Windows has an eBPF project too.

What’s next?

Carol’s exam went smoothly, as it happens, with nobody up all night. Programmable networks change how networks are run. The next chapter changes where they are: thousands of routers in orbit, moving at seven and a half kilometres a second, with the internet handed from one to the next every few seconds.

Three programs, for Linux, run on the Pi. controller.py runs anywhere with Python; the switches need Open vSwitch (sudo apt install openvswitch-switch). ebpf.py needs a Linux kernel from the last few years, and sudo; it works on ARM (like a Pi) and on ordinary x86 PCs.

1. A software-defined network

In one terminal, python3 controller.py. In another, sudo ./sdn_box.sh up and then sudo ./sdn_box.sh test. Watch the controller learn. Stop the controller (Ctrl-C), start it again with --block 10.39.0.3, and test again. sudo ./sdn_box.sh down removes everything.

2. eBPF by hand

sudo python3 ebpf.py count wlan0 (or eth0, or any interface from ip link), then drop, and verifier. To be safe, drop removes itself after 30 seconds; don’t run it on the interface you’re connected through if you change it to drop more than pings!

Experiments

  • Ask Open vSwitch what it would do with a packet, without sending one: sudo ovs-appctl ofproto/trace s1 in_port=1,dl_src=0a:39:00:00:00:01,dl_dst=0a:39:00:00:00:02. Now try a destination the controller hasn’t learned.
  • Add a second cable between s1 and s2, making a loop (Chapter 9). Ping, and watch the controller’s output. What happened, and why don’t the switches’ own rules save you? (A real controller knows the whole topology, so it can compute a tree itself; ours doesn’t.)
  • Turn the learning switch into Chapter 34’s load balancer: when a packet for a “virtual” address arrives, pick a server, and add actions that rewrite the destination address (set_field). You’ll need OpenFlow’s set-field action, type 25.
  • Change the doorman to drop pings from one address only. Or make it count pings by source address, using a hash map (map type 1) instead of an array.
  • Count TCP retransmissions, by destination, for the whole computer: sudo bpftrace -e 'tracepoint:tcp:tcp_retransmit_skb { @[ntop(args->daddr)] = count(); }'. Leave it running while you use a busy Wi-Fi network (Chapter 28), then press Ctrl-C.
