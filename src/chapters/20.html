Home for the weekend

Alice is home for the weekend. Her laptop joins the home Wi-Fi without her touching anything, and Bob, who now checks the router’s device list the way other people check the weather, notices the new arrival.

B: You’re 192.168.1.7. At university you said you were 10.something. A: 10.23.147.8, in the library. At the café on the corner I’m 172.16.5.20. B: So your address changes every time you move. And the router’s settings page says 192.168.1.0/24. What’s the slash for? A: It says where the network part of the address ends. In Chapter 11 we split our addresses neatly at a dot: network 4, host 2. Real addresses can be split anywhere. B: And why is everyone’s house 192.168.1-something? Mine, Grandpa’s, my friend’s… A: Because there aren’t enough addresses to go round. That’s a story for this chapter and the next two.

In Chapter 11, we invented network addresses with two parts: a network number, which routers use to find the right neighborhood, and a host number, for the one computer within it. The real internet’s addresses work the same way. This chapter looks at IPv4, the version of the Internet Protocol that has carried nearly all of the internet’s traffic since 1983: its addresses, how networks are carved out of them, and the 20-byte header on the front of every packet.

Four numbers and a slash

An IPv4 address is 32 bits long. Nobody wants to read 32 ones and zeros, so it’s written as four bytes, each in decimal, with dots between: 192.168.1.3. That’s the whole trick behind the “dotted quad”. Each part is a byte, so each is between 0 and 255.

The number after the slash is the prefix length: how many bits, from the left, are the network part. The rest are the host part. Every computer can work out its own network with a single operation:

This way of writing networks is called CIDR (“classless inter-domain routing”, from 1993; we’ll see what the classes were in a moment). The same network is sometimes written with a netmask instead, especially on older systems: 192.168.1.0 with netmask 255.255.255.0 is exactly 192.168.1.0/24.

Two addresses in every network are special. The one with every host bit set to 0 is the network’s own name, and isn’t given to a computer. The one with every host bit set to 1 is the broadcast address: a packet sent to 192.168.1.255 is for every computer on this network. So a /24 has 256 addresses, and 254 of them can be used. Every extra bit of prefix halves the network. A /23 has 512 addresses, a /25 has 128, a /30 has just 4, which leaves 2 usable addresses, perfect for a cable between two routers. And a /32 is a single address: a network of one.

Here, or somewhere else?

Before sending any packet, a computer asks one question: is the destination on my own network? It ANDs the destination with its own netmask, and compares the result with its own network address. If they match, the destination is right here, on the same Ethernet or Wi-Fi, and the packet goes straight to it (after a “who has?”, Chapter 21). If they don’t, the packet goes to the default gateway, the router, which will worry about where it goes next. Your computer can tell you which it would choose:

$ ip route get 1.1.1.1 1.1.1.1 ⟦1:via 192.168.1.1⟧ dev wlan0 src 192.168.1.4 uid 1000 $ ip route get 192.168.1.3 192.168.1.3 ⟦2:dev wlan0⟧ src 192.168.1.4 uid 1000 $ ip route default via 192.168.1.1 dev wlan0 proto dhcp src 192.168.1.4 metric 600 ⟦3:192.168.1.0/24 dev wlan0⟧ proto kernel scope link src 192.168.1.4 metric 600 1 | 1.1.1.1 isn’t on 192.168.1.0/24, so it goes via the router. 2 | Bob’s laptop is on the same network, so the Pi sends to it directly: no “via”. 3 | The routing table (Chapter 11). This line exists just because the Pi’s address is 192.168.1.4/24: “that whole network is right here, on my Wi-Fi”. The default line catches everything else.

On a Mac, route -n get 1.1.1.1 answers the same question, with gateway: 192.168.1.1.

Bob sets up a new printer by hand, and types its address as 192.168.1.50, but by mistake gives it the netmask 255.255.0.0 (a /16). Everyone on the network can still print to it. So what’s wrong?

The printer now thinks every address from 192.168.0.0 to 192.168.255.255 is on its own network. Printing still works, because all of Bob’s computers really are on 192.168.1.x. But if the printer ever needs to reach, say, 192.168.7.20 on another network (perhaps Grandpa’s house, over a VPN, Chapter 35), it will shout “who has 192.168.7.20?” on the home Wi-Fi instead of asking the router, and nobody will answer. Wrong netmasks cause some of the strangest “it works for everyone except…” problems.

Classes, and why they went away

The original plan, in 1981, was simpler and much more wasteful. The first few bits of an address decided how big its network was. Addresses starting with 0 were class A: a /8, with 16 million addresses each, and only 128 of them in the world. Addresses starting with 10 were class B: a /16, with 65,536 addresses. Addresses starting with 110 were class C: a /24, with 256.

A company that needed 300 addresses was too big for a class C, so it got a class B, and wasted 65,000 addresses. The first organizations on the internet each got a whole class A, and many still have them. By the early 1990s, class Bs were running out fast, and routers were struggling with the number of class Cs. CIDR, in 1993, let networks be any power-of-two size, and let routers combine neighboring networks into one entry. (That’s the “inter-domain routing” part, and it’s Chapters 23 and 24.) 32 bits allow for about 4.3 billion addresses, which seemed like plenty when IPv4 was designed in 1981, for a research network of a few hundred computers. There are now far more phones alone. The central pool, run by IANA, handed out its last blocks in February 2011, and the five regional registries that serve different parts of the world ran out one by one over the following years.

Since then, IPv4 addresses have been bought and sold, often for tens of dollars each. Several of the organizations that got a whole /8 in the early days have sold parts of theirs: MIT sold half of 18.0.0.0/8 in 2017. The real long-term fix is IPv6, with 128-bit addresses (Chapter 25). The short-term fix, which has lasted thirty years so far, is NAT (Chapter 22).

The header, field by field

Every IPv4 packet starts with a header of at least 20 bytes. Here it is, drawn the way the standard draws it, 32 bits to a row, with the real values from the Pi’s request to info.cern.ch from Chapter 16:

  • Version is 4. (IPv6 packets start with a 6, so a computer can tell them apart from the very first four bits.)
  • Header length counts in 4-byte words, so 5 means 20 bytes. It can be bigger if there are options after the addresses, but options are so rarely used today that many routers treat packets with them with suspicion.
  • DSCP marks a packet’s priority, so networks that care can let video calls go ahead of downloads. ECN lets routers warn about congestion without dropping packets (Chapter 28).
  • Total length is the whole packet, header and all: at most 65,535 bytes, though packets that big are never sent in practice.
  • Identification, flags and fragment offset are for chopping packets up, below.
  • Time to live is Chapter 11’s hop limit: every router takes one off, and throws the packet away at zero.
  • Protocol says what’s inside: 1 for ICMP (Chapter 21), 6 for TCP, 17 for UDP.
  • Header checksum is Chapter 10’s Internet checksum, of the header only. Because every router changes the time to live, every router has to fix the checksum too.
  • The source and destination addresses stay the same from one end to the other. At least, that was the plan. Chapter 22 is about the box that breaks it.

Too big to fit

Every link has a maximum transmission unit, or MTU: the biggest packet it can carry in one frame. For Ethernet and Wi-Fi it’s 1,500 bytes. For Bob’s PPPoE internet connection, it’s 1,492 (Chapter 18). What happens when a packet is too big for the next link? In IPv4, the router can chop it into fragments, each a complete little packet with its own header. Here’s a real one, from the Pi:

$ sudo tcpdump -i wlan0 -n -v icmp & $ ping -c 1 -s 3000 1.1.1.1 23:52:34.703316 IP (tos 0x0, ttl 64, ⟦1:id 32267, offset 0, flags [+]⟧, proto ICMP (1), length 1500) 192.168.1.4 > 1.1.1.1: ICMP echo request, id 15084, seq 1, length 1480 23:52:34.703330 IP (tos 0x0, ttl 64, id 32267, offset 1480, flags [+], proto ICMP (1), length 1500) 192.168.1.4 > 1.1.1.1: ⟦2:ip-proto-1⟧ 23:52:34.703332 IP (tos 0x0, ttl 64, id 32267, offset 2960, ⟦3:flags [none]⟧, proto ICMP (1), length 68) 192.168.1.4 > 1.1.1.1: ip-proto-1 23:52:34.721734 IP (tos 0x0, ttl 58, id 57636, offset 0, flags [+], proto ICMP (1), ⟦4:length 1492⟧) 1.1.1.1 > 192.168.1.4: ICMP echo reply, id 15084, seq 1, length 1472 23:52:34.721767 IP (tos 0x0, ttl 58, id 57636, offset 1472, flags [+], proto ICMP (1), ⟦4:length 28⟧) 1.1.1.1 > 192.168.1.4: ip-proto-1 …three more pieces… 1 | All three pieces share identification 32267. [+] means “more fragments are coming”. 2 | Only the first fragment has the ICMP header in it, so tcpdump can’t say much about the others. (That’s why the packet filter in Chapter 16 checked the fragment offset before looking for port numbers.) 3 | The last piece: no “more” flag. 4 | The reply’s pieces were cut again, into 1,492 and 28 bytes, by a router in front of the 1,492-byte link.

Fragmentation works, but it causes trouble. If any fragment is lost, the whole packet is lost, and a lost fragment can’t be resent on its own. Firewalls and load balancers can’t see port numbers in the later pieces. Attackers have abused overlapping fragments to sneak past security checks. So modern computers avoid it. They set the don’t fragment flag on their packets (it was set on the Pi’s request to CERN), and if a packet is too big, the router throws it away and sends back a “too big, the limit here is 1,492” message instead. That’s path MTU discovery, which you saw in Chapter 10’s lab, and it’s why the ping above had to be deliberately oversized. IPv6 went further, and doesn’t let routers fragment at all.

What’s next?

Twice in this chapter we skipped over the “who has?” that happens before a packet goes anywhere, and the “too big” and “time exceeded” messages routers send back. They’re the small talk of the internet, and Chapter 21 is about them: ARP and ICMP, and how ping and traceroute really work.

Experiments

  • Work out by hand how many usable addresses a /20 has, and what the netmask is. Check with ipcalc.py.
  • Add a --join option that takes two neighboring networks, like 192.168.0.0/24 and 192.168.1.0/24, and says whether they can be combined into one shorter prefix. That’s exactly what routers do to keep their tables small (Chapter 23).
  • In reassemble, remove one piece from the list before gluing. What happens? Real computers wait about 30 seconds for missing pieces, then give up. Why not wait forever?
  • Ping with “don’t fragment” and a size that’s too big: ping -D -s 1472 1.1.1.1 on a Mac, or ping -M do -s 1472 1.1.1.1 on Linux. On a 1,492-byte connection it fails, and 1,464 works. Watch it with tcpdump to see the router’s “too big” message.
