A machine that can be anything

The Chatterbox does one thing well: you type, the other side prints. But Alice and Bob keep wanting it to do new things. Alice wants to send Bob her book report, three pages long, without retyping it. Bob wants to play chess over the wire. Carol, who just moved in down the street, asks whether the Chatterbox can send drawings.

Every one of those means building a new machine. Unless, that is, you build a machine that can become whatever machine you need.

That’s what a computer is. A computer is a machine that follows a list of instructions, called a program, and you can give it a different program whenever you like. The same box that runs a chat program today can run a chess program tomorrow. The hardware stays the same, and the software decides what it does.

Alice and Bob each get a computer. Here’s what’s inside:

  • The CPU (central processing unit) reads instructions one after another and carries them out, billions per second.
  • Memory holds the program that’s running and the data it’s working on. It forgets everything when the power goes off.
  • The disk holds files: named chunks of data that stay put when the power goes off.
  • The keyboard and screen let people talk to it.
  • The network card is our old transceiver chip on a little board that plugs into the computer. It still does everything from Chapters 2 and 3: bit timing, start pulses, collisions, backoff and framing.

Notice where the network card sits: at the bottom, next to the disk and keyboard. As far as the CPU is concerned, it’s just another device you can hand data to and get data from. The layers from Chapter 1 are still there. They’ve just moved into hardware.

Programs

When Alice switches her computer on, it shows a prompt and waits. She types the name of a program and presses Enter, and the computer runs it. This typing-commands-at-a-prompt setup is called a shell or a terminal.

The first program Alice’s cousin writes is CHAT. It does exactly what the Chatterbox did: whatever you type goes to the other computer, and whatever arrives gets printed. Only now it’s a few hundred lines of software instead of a machine.

$ CHAT CHAT IS RUNNING. TYPE A MESSAGE AND PRESS ENTER. > ARE YOU THERE? BOB: YEP. NEAT, IT WORKS.

Nothing about the wire changed. CHAT hands each message to the network card, and the network card frames it with ~S and ~E and sends it bit by bit, exactly as before.

The first message ever sent between two computers on the ARPANET, the ancestor of the internet, went from UCLA to the Stanford Research Institute on October 29, 1969. The plan was to type LOGIN. The operator typed L, then O, and then the system at the other end crashed. So the first message on the internet’s ancestor was “LO”, as in “lo and behold”. They got the whole word through about an hour later.

Files

Alice’s second program is WRITE, a simple text editor. She types her book report in it and saves it on the disk as a file called REPORT. A file is just a named sequence of symbols. Since a file can have more than one line, we need a way to mark the end of each line, so we add one more control code: ~L means “new line”.

Bob has written a report too, and Alice would like to read it before school. Bob could open CHAT and type the whole thing out by hand, but that would be silly: the report is already sitting on his disk. What Alice really wants is to tell Bob’s computer “please send me the file called REPORT”, and have it happen even while Bob is asleep.

May I have that, please?

This calls for a new kind of program, one that doesn’t wait for a person to type anything. It waits for messages, and answers them.

Bob runs a program called SERVE. It sits in the background, listening for requests coming in over the wire. Alice runs a program called FETCH. When she types FETCH REPORT, FETCH sends a request to Bob’s computer asking for the file, waits for the answer, and saves what comes back onto Alice’s disk.

The two programs need a protocol so they understand each other. Here’s the request FETCH sends, one line per row:

request | GET request | REPORT

The first line is the command, GET, and the second is the name of the file. If SERVE finds the file, it replies with a status line, the file name, and then the contents of the file:

status | OK status | REPORT body | BOOK REPORT: TREASURE ISLAND body | by Bob body | …

And if there’s no such file, it says so:

status | NOT FOUND status | REPORT

This pattern is so common it has names. The program that waits and answers is the server, and the program that asks is the client. Each exchange is a request followed by a response. Most of what you do on the internet follows this pattern: your web browser is a client, and every website is a server.

Look at how the request is laid out, too: a command, then details about what the command applies to. That shape will stay with us all the way to the real web, where your browser sends requests that start with the very same word, GET.

Special delivery

Fetching works so well that they add the opposite: STORE, a client that sends a file to the other computer. When Alice types STORE NOTES, it sends this:

request | PUT request | NOTES body | Things to remember: body | - bring snacks

and SERVE saves the file and replies OK.

Bob immediately spots a danger. If SERVE will save any file anyone sends, then anyone on the wire can overwrite anything on his disk, including his own report, the night before it’s due. So he adds a rule: SERVE only ever saves incoming files into a folder called INBOX. Whatever arrives lands there, and Bob decides what to do with it.

That’s our first bit of network security: a server has to be careful about what strangers are allowed to ask it to do. It won’t be the last. There’s a sneakier hole in SERVE that you’ll find (and fix) in this chapter’s lab.

Many programs, one computer

A problem shows up on the first evening. Bob wants to leave SERVE running all the time so Alice can fetch files whenever she likes. But while SERVE is running, Bob can’t use CHAT. The computer can only run one program at a time.

The fix is a special program that’s always running, in charge of all the others: the operating system, or OS. The OS does two big jobs.

First, it shares the CPU. It lets each program run for a tiny slice of time, a few thousandths of a second, then pauses it and lets the next one run, round and round. It switches so fast that CHAT, SERVE and WRITE all seem to be running at once. This is called multitasking.

Second, it owns the hardware. Programs are no longer allowed to poke the disk or the network card directly, because two programs doing that at once would trip over each other. Instead a program asks the OS (“please send this message”, “please read the file REPORT”), and the OS does it on the program’s behalf.

That’s yet another layer. Programs on top, the OS in the middle, hardware at the bottom.

Who’s this one for?

Multitasking creates a new puzzle. Suppose Bob is running both CHAT and SERVE. A message arrives from the wire. Which program should get it? The network card has no idea. It just knows some bits arrived.

The fix is to put a label on every message saying which program it’s for. Before anything else, every message now starts with two header lines, added by the OS:

header | TO: SERVE header | FROM: FETCH#2 request | GET request | REPORT

TO says which program on the other computer should get the message. FROM says which program sent it, so the answer can find its way back. When a message arrives, the OS works like a mailroom: it reads the TO line and drops the rest of the message into that program’s mailbox.

About that #2. Suppose Alice fetches REPORT and SCHEDULE at the same time, in two separate FETCH programs. Both replies come back addressed TO: FETCH. Which one is which? The OS can’t tell, and the first FETCH might end up saving SCHEDULE under the name REPORT.

So the OS gives every running program its own unique name by adding a number: the first FETCH is FETCH#1, the second is FETCH#2, and so on. Each one puts its own unique name in the FROM line, and replies come back addressed to exactly the right copy. SERVE doesn’t need a number, because there’s only ever one of it, and everybody needs to know where to find it. Hang on to this idea: a well-known name for servers, and unique throwaway names for clients. In Chapter 12 the names become numbers called ports, and they work exactly this way.

Envelopes inside envelopes

Let’s step back and look at one complete message as it crosses the wire. It’s built in layers, and each layer wraps the one inside it:

When FETCH wants to send a request, it writes GET REPORT and hands it to the OS. The OS wraps it in the TO/FROM header and hands it to the network card. The network card wraps that in ~S and ~E, escapes any ~, and sends it as voltages. On Bob’s side the whole thing happens in reverse: his network card removes the frame, his OS reads and removes the header, and SERVE receives just GET REPORT.

Wrapping data in layer after layer of headers like this is called encapsulation. It’s the same layering as Alice, Max and Grandpa Otto in Chapter 1, except that now you can see each layer’s contribution in the message itself. Every layer adds a wrapper that only its partner on the other side ever reads. SERVE never sees ~S. The network card never looks at the word GET.

Real internet messages are built exactly this way, only with more layers. Part II is largely about opening those envelopes one at a time.

Nobody home

One last detail. What happens if Alice runs FETCH REPORT but Bob forgot to start SERVE? Bob’s OS gets a message for SERVE, finds nobody running with that name, and throws it away. Nothing comes back.

Alice’s FETCH can’t wait forever, so it uses the timeout trick from Chapter 3. If there’s no reply within a few seconds, it gives up and prints NO ANSWER FROM THE OTHER COMPUTER.

Notice that there are two different kinds of “no”:

  • NOT FOUND means SERVE is running and answered, but there’s no such file. That’s a clear, definite answer.
  • Silence means something went wrong along the way: SERVE isn’t running, the computer is off, the wire is cut, or the request was lost. FETCH can’t tell which.

It’s the dark window from Chapter 1 all over again. A real answer, even “no”, is far more useful than silence. That’s why servers go to the trouble of replying NOT FOUND instead of just ignoring requests they can’t fulfill.

The first internet protocol for moving files, FTP (File Transfer Protocol), was described in 1971 in RFC 114. It’s still around today. FTP servers answer with three-digit numbers instead of words, like 550 for “file unavailable”, so that programs can check them easily. The web’s HTTP protocol, which we’ll reinvent in Chapter 6 and meet for real in Chapter 30, borrowed that idea. That’s where the famous 404 Not Found comes from.

Our ~L line breaks live on too. Many internet protocols, HTTP and email included, end each header line with two ASCII control characters, CR and LF (“carriage return” and “line feed”). Those names come straight from teleprinters, where one moved the print head back to the left margin and the other rolled the paper up one line.

What’s next?

Alice’s computer can now fetch files, store files and chat, all at the same time. She reads Bob’s report, and on the last line she finds: “See SCHEDULE for when we are presenting this to the class.” So she has to type FETCH SCHEDULE, which might mention yet another file, and so on. And she only knew the file was called SCHEDULE because the report told her. How is she supposed to find out what files Bob has in the first place? Hold that thought; it leads somewhere big in Chapter 6.

First there’s a more basic problem. Carol has drawn a picture of a volcano for Alice’s class presentation, and she wants to send it over. But our computers still speak the 32-symbol codebook from Chapter 1. It has no lowercase letters and no digits, and certainly no way to describe a picture. In the next chapter we’ll give our computers a much bigger vocabulary, and teach them to send anything.

This is the first lab where two programs really talk to each other. Each copy of computer.py is one “computer”: it has an operating system with a mailroom, a disk (a folder), a shell you can type commands into, and a wire to the other computer. The programs from this chapter (SERVE, FETCH, STORE and CHAT) run inside it as background threads.

One confession first: for the wire, we’re borrowing a real network connection between two programs on your own machine, a TCP socket on 127.0.0.1. That’s cheating a bit, because it quietly handles all the reliability problems from Chapter 3 for us. We’ll build that machinery ourselves in Part I and then take the real thing apart in Part II. For now, treat it as a very well-behaved wire.

1. Two computers, two terminals

Open two terminal windows. In both, go to labs/ch04. Start Alice first, since her computer waits for the wire to be plugged in:

$ python3 computer.py alice --disk alice_disk --listen 7000 waiting for the other computer to plug into port 7000... $ python3 computer.py bob --disk bob_disk --connect 7000 wire connected. type HELP for commands. bob>

Now, on Alice’s computer, try to fetch something before Bob starts his server:

alice> FETCH REPORT [alice OS] FETCH#1: no answer from the other computer (is SERVE running there?)

and look at what Bob’s OS says about it:

[bob OS] dropped a message for 'SERVE': no program by that name is running

Now start the server on Bob’s side (START SERVE) and try again from Alice: FETCH REPORT, then SHOW REPORT. Also try FETCH HOMEWORK (it doesn’t exist), STORE NOTES (then run LS on Bob’s side to find it in the INBOX), and CHAT with a message that contains a ~. Use PS to see which programs are running, and notice the numbers on FETCH and STORE.

3. Speak the protocol by hand

You don’t need a FETCH program to fetch a file. You just need to send the right symbols. Quit both computers. In terminal 1, instead of Alice’s computer, run nc (netcat), a tool that connects your keyboard straight to a network connection:

$ nc -l 127.0.0.1 7000

(The 127.0.0.1 matters on a Mac. macOS’s AirPlay Receiver listens on port 7000 too, and a plain nc -l 7000 fails with “Address already in use”. Asking specifically for the loopback address sidesteps it. There’s more about nc in the Field Guide.)

Start Bob’s computer in terminal 2 as before, and type START SERVE there. Then go back to terminal 1 and type a complete request by hand, all on one line, then press Enter:

~STO: SERVE~LFROM: ME~LGET~LSCHEDULE~E ~STO: ME~LFROM: SERVE~LOK~LSCHEDULE~LCLASS PRESENTATIONS~LMonday: Alice (volcanoes)~LTuesday: Bob (Treasure Island)~LWednesday: Carol (how bees talk)~E

The second line is Bob’s answer, exactly as it came over the wire. You’re now speaking the protocol yourself. Try a PUT by hand, then send something malformed and see how SERVE reacts.

4. Find the hole in SERVE

Bob’s SERVE is only supposed to share files from bob_disk. There’s also a file called SECRET in the lab folder, one level above Bob’s disk. From Alice’s computer, try:

alice> FETCH ../SECRET

Uh oh. SERVE builds the path by gluing the requested name onto bob_disk/, and .. means “the folder above”. This is a real and very common class of security bug called path traversal, and servers on the internet have been caught by it many times. Fix serve() so it refuses any file name that isn’t a plain name inside the disk folder. (Hint: compare the name with os.path.basename(name), or check that os.path.realpath() of the full path starts with the disk folder’s real path.) Then try the attack again.
