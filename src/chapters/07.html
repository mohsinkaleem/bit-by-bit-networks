A page that’s never the same twice

Bob got a digital thermometer for his birthday and stuck it outside his window. It plugs into his computer, which can read the temperature whenever it likes. Naturally, Bob wants a page on his little web that shows the current temperature.

But what file would that be? He could write the temperature into a file called weather.mu, but the file would be out of date a minute later. He’d need to rewrite it constantly, day and night, just in case somebody looks.

The better idea is to turn the question around. Instead of preparing the page in advance, Bob’s server could make it at the moment someone asks for it. When a request for /weather arrives, the server doesn’t look for a file at all. It runs a small program that reads the thermometer, writes a fresh page containing the reading, and sends that back.

A page produced like this is called dynamic, and a page that’s just a file on disk is static. Look at it from the browser’s side, though. It sent GET /weather and got back a document with a Type and a Length. It can’t tell, and doesn’t care, whether that document came from a disk or was written a millisecond ago. The protocol is exactly the same.

Asking with details

The /dice page above needs to know how many sides the dice have and how many to roll. Bob’s weather page could show Celsius or Fahrenheit. How does the browser say which it wants?

By tacking extra information onto the end of the URL. After the path comes a ?, then name=value pairs separated by &:

These are called query parameters, and the part after the ? is the query string. The server splits it apart and hands the pieces to the program.

One wrinkle: what if a value itself contains a &, a = or a space? “fish & chips” would be split in the wrong place. So those characters get written in a special way: a % followed by the character’s byte value in hex (Chapter 5 pays off). A space becomes %20, & becomes %26, and an emoji becomes its UTF-8 bytes, one % at a time. This is called percent-encoding, and it’s the escaping trick from Chapter 3 all over again. Try it:

Signing the guestbook

Carol wants a guestbook on her page: visitors type their name and a message, and it gets added to the list for everyone to see. That’s a new kind of request. Up to now, the browser has only ever asked for things. This time it needs to send something that changes what’s stored on the server.

We could cram the message into a query string, GET /guestbook?name=Alice&message=Hi, but that would be a bad idea, for reasons we’ll see in a moment. Instead we use a different method. Instead of GET, the request starts with POST, which means “here is some data for you to do something with”, and the data travels in the request’s body, just like a reply’s body:

request | POST /guestbook TTP/1 header | Host: carol header | Type: application/x-www-form-urlencoded header | Length: 30 blank | (blank line) body | name=Alice&message=Hi+Carol%21

The body uses the same name=value&name=value format as a query string (with + as an extra shorthand for a space). To let visitors fill it in, the markup language gets a new tag, a form, which draws some text boxes and a button, and sends a POST when the button is pressed.

There’s one subtle trap. After the server saves the message, what should it reply? If it replied with the updated guestbook page, the browser would be showing the result of a POST. And if Alice then pressed Reload, her browser would re-send that POST, and her message would appear twice. That’s the duplicates problem from Chapter 3, caused by the user this time instead of a lost acknowledgement.

So the server instead replies with a special redirect, 303 See Other, meaning “done; now go and GET the guestbook”. The browser does, and what Alice ends up looking at is the result of a harmless GET:

Some requests are safer than others

Why was it a bad idea to sign the guestbook with a GET? Because programs other than people follow links. Remember the “spider” from the last chapter’s lab, which visits every link it can find? If signing the guestbook were a link, the spider would sign it. So would any browser that fetches links ahead of time to make pages load faster. If there were a GET /delete-everything link, a spider would happily delete everything.

So everyone agrees on a rule: GET must never change anything. Reading is always safe to repeat. That’s why the browser warns you before re-sending a POST but reloads a GET without a second thought.

Once there are methods that change things, it’s worth sorting them by one more property, idempotence: does doing it twice have the same effect as doing it once?

MethodMeansSafe? (changes nothing)Idempotent? (twice = once)
GETgive me this✔✔
PUTstore this, replacing whatever is there✘✔ (the second copy just replaces the first)
DELETEremove this✘✔ (it’s just as gone the second time)
POSThere’s some data; do something with it✘✘ (sign the guestbook twice, get two entries)

This matters a lot for the retry problem from Chapter 3. If a request might have been lost, is it OK to just send it again? For an idempotent request, yes: at worst it happens twice, and twice is the same as once. For a POST, a retry might mean two guestbook entries, or two payments. Keep this in the back of your mind; it’ll come back when we build reliable delivery in Chapter 13.

Who are you again?

Bob wants his server to say “Welcome back!” to people who have visited before. But there’s a problem: the server has no memory of who it’s talking to. Every request arrives on its own, with no connection to the ones before it. Alice’s second visit looks exactly like a stranger’s first. The protocol is stateless.

Being stateless is actually a strength. The server doesn’t have to keep track of millions of conversations, and if it restarts, nothing is lost. But sometimes you do want the server to recognize someone, for example to keep someone logged in, or to remember what’s in their shopping basket.

The trick is to have the browser do the remembering. The first time Alice visits, the server makes up a number for her and sends it back in a new header, Set-Cookie: visitor=7. Her browser stores it. From then on, every request her browser sends to that server carries it: Cookie: visitor=7. It works like a cloakroom ticket, where the server hands you a number and you show it every time you come back.

Logging in to a website works exactly this way. When you type your password correctly, the server hands your browser a long, random, unguessable cookie, and from then on that cookie is your proof of who you are. That means anybody who steals the cookie can pretend to be you, so it’s extremely important that nobody else sees it. Keep that in mind for Chapter 32.

Cookies were invented in 1994 by Lou Montulli at Netscape, to let online shops remember a shopping cart. They were soon put to a less friendly use. A page can include images or scripts from other servers, such as an advertising company’s, and those requests carry that company’s cookie. Because the same ad company’s content appears on thousands of sites, its cookie lets it follow one person across all of them. These “third-party cookies” are why browsers such as Safari and Firefox now block them by default, and why you see so many cookie consent banners.

Never trust the guestbook

Within a day of the guestbook going up, Eve signs it. Her “message” is:

body | Great page! <link to="ttp://eve/prize.mu">Click here to claim your prize</link>

Carol’s server stores it, and then pastes it straight into the guestbook page. Every visitor’s browser sees Eve’s tags and obeys them, so now Carol’s page contains a link that Carol never wrote, to wherever Eve likes. Eve could just as easily have added an <image> tag pointing at her own server, which would tell her every time someone viewed Carol’s page.

pasted in as-is
• Alice: Hi Carol! Love the bees
• Eve: Great page! Click here to claim your prize
escaped first
• Alice: Hi Carol! Love the bees
• Eve: Great page! <link to="ttp://eve/prize.mu">Click here to claim your prize</link>

The problem is that the server mixed data (someone’s message) with instructions (markup) without marking which was which. The fix is escaping, once again. Before putting a visitor’s text into a page, the server replaces every < with a code that displays as < but isn’t treated as the start of a tag. Now Eve’s message shows up as the harmless, slightly embarrassing text it is.

The broader lesson is one of the most important in all of computer security: never trust anything that came over the network. Escape it before you display it. Check that it’s the size and shape you expected (the lab’s dice page refuses a million-sided die). Assume someone like Eve is on the other end.

Eve’s trick is a real and very common attack called cross-site scripting (XSS). In real HTML, an attacker can inject not just links but <script> tags, which run code in every visitor’s browser, and that code can read the visitor’s cookies. Its cousin, SQL injection, sneaks commands into data that a server passes to its database. Injection bugs of one kind or another have been near the top of every list of the most dangerous web vulnerabilities for over twenty years.

When you don’t know how long it’ll be

Back in Chapter 5 we chose to frame messages by sending a Length up front, with a warning: “the sender needs to know the length before it starts”. For a file on disk, that’s easy. For a dynamic page, the server might not know until it’s finished writing it. And some responses never finish at all, like a live news feed or a video stream.

The answer is to send the body in pieces, called chunks, each with its own length in front. A chunk of length zero means “that was the last one”:

It’s still length-first framing, so there’s no escaping and no scanning, just applied one piece at a time. The server can start sending the top of a page before it has worked out the bottom, and the browser can start showing it straight away. The lab’s /countdown page does this: it sends one line a second, and your browser displays each line the moment its chunk arrives.

Everything in this chapter is part of the real web. Letting a web server run programs was standardized in 1993 as CGI (the Common Gateway Interface). Languages like PHP (1995) made it easy, and today almost every page you visit is produced on the fly by frameworks like Django, Rails or Express. HTTP defines GET, POST, PUT, DELETE and a few others (HEAD, PATCH, OPTIONS), and the specification formally defines which of them are “safe” and “idempotent”, just as we did. The chunked sending you just saw is HTTP/1.1’s Transfer-Encoding: chunked.

What’s next?

Look at what our little network does now. Browsers, links, pictures, pages that write themselves, forms, cookies. It’s a real web, just a small one. There’s an elephant in the room, though. All of it runs over a single wire between two houses. Carol’s pages live on Bob’s computer because Carol has no way to connect.

Carol wants in, and so does Dave from across the road. But every protocol we’ve built assumes exactly two computers, one at each end of a wire. In the next chapter, three becomes a crowd.

2. Talk to it with curl

curl shows you what’s really going on. -i prints the reply’s headers, -d sends a POST body, and -c/-b save and send cookies from a file:

$ curl -i "localhost:7007/dice?sides=20&n=3" HTTP/1.1 200 OK Connection: close Content-Type: text/html; charset=utf-8 Content-Length: 380 … $ curl -i localhost:7007/hello | grep -i cookie Set-Cookie: visitor=1; Path=/; Max-Age=86400 $ curl -c jar -b jar localhost:7007/hello > /dev/null $ curl -c jar -b jar -s localhost:7007/hello | grep -o "Welcome back.*" Welcome back, visitor #2. This is visit number 2. $ curl -i -d "name=Alice&message=Hi+Carol%21" localhost:7007/guestbook HTTP/1.1 303 See Other Connection: close Location: /guestbook Content-Length: 0

And here’s chunked sending, with --raw so curl shows you the chunk lengths instead of hiding them. Watch the lines appear one second apart:

3. Break the guestbook, on purpose

Stop the server, set ESCAPE_GUESTBOOK = False near the top of dynserver.py, and start it again. Now sign the guestbook with a message containing HTML, like <b style="color:red">BIG RED TEXT</b>, then with <script>alert("Eve was here")</script>. Reload the guestbook. Every visitor would now run Eve’s code. Set ESCAPE_GUESTBOOK back to True and look again: the same stored messages are now harmless text. (Delete guestbook.json to clear the guestbook.)

4. Make your own dynamic page

Add a /counter page that shows how many times it has been visited in total, by anyone. Then add /greet?name=…, which says hello to whoever is named in the query string. Did you remember to escape the name? Try /greet?name=%3Cb%3EEve%3C%2Fb%3E to check.
