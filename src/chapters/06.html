What’s on the menu?

Carol now has a computer too, and she’s filling it with drawings, recipes and notes about bees. It isn’t connected to the wire yet (that’s a bigger job than it sounds, and it gets its own chapter), so for now Bob has offered to keep a copy of Carol’s pages on his computer, where Alice can reach them. Between the three of them there are dozens of files, and a familiar problem keeps coming up: you can only fetch a file if you already know its name.

The simplest fix is to let the server tell you. Bob’s cousin (who keeps upgrading everything) adds a new command to SERVE. When a client asks for LIST, SERVE replies with a plain text document that names every file it’s willing to share:

status | OK header | Type: text/plain header | Length: 71 body | index.mu body | report.mu body | schedule.mu body | school/ (a folder) body | volcano.png

Bob has started keeping files in folders (also called directories), so a file’s full name now includes the folders it’s in, separated by slashes: /school/homework.mu. The leading slash means “starting from the top folder”. A name like this is called a path, because it’s the route you follow through the folders to reach the file.

Bob also adds one small convenience. If you ask for a folder instead of a file, SERVE sends back a file called index.mu from that folder, if there is one. That gives every folder a sort of front page. Asking for / gets Bob’s front page.

Documents that point at each other

A list of files is better than nothing, but Bob’s report still ends with “see SCHEDULE”, and Alice still has to go and fetch it by hand. What if the report could point at the schedule in a way that a program understands?

To do that, the document needs two kinds of text mixed together: the words meant for people, and little instructions meant for the program displaying it. We need a way to tell them apart. We’ll use angle brackets: anything between < and > is an instruction, called a tag. Everything else is ordinary text. Our first few tags:

  • <title>…</title>: the document’s title
  • <h>…</h>: a heading, shown big
  • <b>…</b>: bold
  • <link to="schedule.mu">…</link>: the words in between are a link. Selecting them should fetch schedule.mu.
  • <image src="volcano.png">: show a picture here (fetched from volcano.png)

A tag that starts something has a matching tag with a slash that ends it. Text written this way is called markup, since it’s “marked up” with instructions, and we’ll give it its own media type, text/markup, with file names ending in .mu. Here’s Bob’s report, before and after:

what the file contains
<title>Book report</title>
<h>Book report: Treasure Island</h>
by <b>Bob</b>

Jim Hawkins finds a map, a ship
full of pirates, and a parrot...

See the <link to="schedule.mu">schedule</link>
for when we present.
what Alice sees

Book report: Treasure Island

by Bob

Jim Hawkins finds a map, a ship full of pirates, and a parrot…

See the schedule for when we present.

The file itself is still just text, so you can write it in any editor. What makes it come alive is a program that understands the tags.

A program for following links

That program is a browser. Alice’s cousin writes one, and it does four things over and over:

  1. Fetch a document from a server.
  2. Display it, following the tags: big headings, bold words, pictures in place, links underlined.
  3. Wait for Alice to pick a link.
  4. Work out what the link points to, and go back to step 1.

It also remembers where Alice has been, so a Back button can take her to the previous page. That’s it. Alice can now start at Bob’s front page and wander through everything he’s shared without typing a single file name.

There’s one surprise hiding in step 2. A picture isn’t inside the markup document; the <image> tag only says where to find it. So when the browser comes across an image tag, it makes a whole separate request to fetch the picture. A page with ten pictures takes eleven requests. Step through a visit to Bob’s page:

Links to other computers

Bob’s schedule wants to link to Alice’s volcano notes and Carol’s page about bees, and those live on other computers. A link that just says volcanoes.mu would send the browser looking for that file on Bob’s computer.

So a full link needs to say which computer too. And while we’re at it, it should say which protocol to use, in case we invent others later. The three pieces get squashed into one string:

This string is called a URL, for Uniform Resource Locator. We’re calling our protocol the Tangled Text Protocol, so our URLs start with ttp://. The host names (alice, bob, carol) are just the computers’ names for now. How a name turns into an actual machine on a big network is a whole story of its own, told in Chapter 14.

Links in a document can come in three flavors:

  • Absolute, like ttp://carol/bees.mu: a completely different computer.
  • Root-relative, like /index.mu: the same computer, starting from its top folder.
  • Relative, like schedule.mu: the same computer and the same folder as the current page.

Relative links are handy: Bob can move his whole school folder somewhere else, and the links between the files inside it keep working.

A web of documents

Something interesting happens once Alice, Bob and Carol start linking to each other’s pages. Nobody is in charge of the overall structure. Each of them just adds links to whatever they find useful. But put all those links together and the documents form a tangled, growing web, spread across all their computers:

That lack of a plan is its greatest strength. Anybody can add a page and link to anything, without asking permission. The price is broken links: when Carol deleted her old drawings page, the link on her front page kept pointing at it. Nothing checks links ahead of time. You only find out a link is broken when you follow it and the server says it can’t find the page.

Say it with numbers

Speaking of which: our replies have been saying OK and NOT FOUND in words. Now that browsers need to react automatically (following redirects, showing a sensible error page), it helps to use numbers. A browser can compare numbers reliably, and a number can come with a word attached for humans. We give every reply a three-digit status code, grouped by the first digit:

CodeMeaningExamples
2xxSuccess: here you go200 OK
3xxGo somewhere else301 Moved Permanently (plus a Location header)
4xxYou asked for something wrong404 Not Found, 400 Bad Request
5xxThe server broke, not your fault500 Internal Server Error

A browser that has never seen a particular code can still act sensibly just by looking at the first digit. A 418 is some kind of mistake on your end, whatever else it means.

The browser talks too

So far the browser’s request has been a single line. But the server could do a better job if it knew a little more about who’s asking, so the request grows headers too, just like the reply did in Chapter 5. Here’s a complete conversation in the Tangled Text Protocol:

request | GET /report.mu TTP/1 header | Host: bob header | Accept: text/markup, image/png header | User-Agent: alices-browser/1.0 blank | (blank line) status | TTP/1 200 OK header | Type: text/markup header | Length: 312 blank | (blank line) body | <title>Book report</title> …
  • The first line is the method (GET), the path, and the protocol version. Putting the version in means we can change the protocol later without confusing old programs.
  • Host says which site the browser meant. That sounds redundant, since the request already arrived at a particular computer. But it lets one computer serve several sites, and that’s exactly what Bob is doing for Carol right now. Requests for ttp://carol/… and ttp://bob/… both arrive at Bob’s computer, and Host tells his server which folder to look in.
  • Accept lists the kinds of data the browser can handle.
  • User-Agent says which browser is asking. It’s mostly useful to the server for keeping statistics.

You have, of course, just reinvented the World Wide Web. In 1989, Tim Berners-Lee, a software engineer at CERN, the physics laboratory near Geneva, proposed a system to help researchers find each other’s documents. By the end of 1990 he had written the three pieces you just built:

  • HTML (HyperText Markup Language), our markup. In real HTML, a link is <a href="…">, a heading is <h1>, and an image is <img src="…">.
  • HTTP (HyperText Transfer Protocol), our TTP. Real requests start with GET /report.html HTTP/1.1 and carry Host, Accept and User-Agent headers. The reply’s headers are Content-Type and Content-Length.
  • URLs, like https://www.example.com/docs/intro.html.

The ideas were older still. In 1945, Vannevar Bush imagined a desk-sized machine called the Memex for following trails between documents, and Ted Nelson coined the word hypertext in the 1960s. The web’s trick was to make it simple enough that anyone could put up a server.

A modern web page is our <image> problem on a massive scale: a typical page makes around 70 separate requests, for pictures, fonts, style sheets and scripts. A lot of the engineering in Chapters 30 and 33 is about making all those requests faster.

And no, the 404 code isn’t named after a room at CERN where the web’s servers lived. That’s a popular myth. The status codes were simply designed in numbered groups, like ours.

What’s next?

Alice, Bob and Carol now have a little web of their own. They can browse each other’s documents, follow links from computer to computer, and see pictures on the page. But every document is a fixed file sitting on a disk. It says exactly the same thing to everyone, every time, until someone edits it.

Bob has an idea for a page that’s different every time you look at it: his thermometer’s current reading. Carol wants a page where visitors can leave messages. Neither can be a file on a disk, because nobody knows what it should say until somebody asks. In the next chapter, we teach servers to write documents on the spot.

This lab gives you the whole web from this chapter: a server that hosts all three computers’ sites (each folder in sites/ is one computer), a browser that runs in your terminal, and one surprise at the end.

1. Start the server

$ cd labs/ch06 $ python3 webserver.py serving alice, bob, carol on port 7006. Ctrl+C to stop.

2. Browse, in the terminal

Our browser is about 150 lines. The two most important pieces work out where a link points, and fetch a URL, following redirects:

$ python3 browser.py ════════════════════════════════════════════════════════════════ Bob's corner of the web ttp://bob/index.mu ════════════════════════════════════════════════════════════════ WELCOME TO BOB'S COMPUTER! Things you can read here: - my book report[1] (due Tuesday) - the class schedule[2] - my homework notes[3] - Carol's page[4] has recipes and bees - Alice's page[5] [picture: /volcano.png, image/png, 944 bytes] (Volcano by Carol.) ──────────────────────────────────────────────────────────────── 2 request(s) for this page link number, b(ack), g , r(eload), q(uit)> 3

Follow links by number and watch the server’s log in terminal 1. Then restart the browser with -v to see every request and reply in full. Things to find:

  • Following link 3 takes two requests. Why? Find both of them in the server log.
  • Go to Carol’s page and follow her old drawings link. What does the server log say?
  • Type g ttp://bob/volcano.png. What does the browser do with a picture it can’t display?

3. Write a page

Create sites/alice/about.mu with a title, a heading, some bold text, and links to at least one page on each of the other two computers. Add a link to it from sites/alice/index.mu. You don’t need to restart the server; it reads files fresh on every request. Now visit it with g ttp://alice/index.mu.

Then make Bob’s old path /report.mu redirect somewhere new: move the file into sites/bob/school/ and add an entry to the MOVED table at the top of webserver.py. Do the links on Bob’s front page still work?

4. The surprise

With webserver.py still running, open this in your normal web browser (Safari, Chrome, anything):

$ open http://localhost:7006/

That’s your server, showing Bob’s page with Carol’s volcano, and all the links work. Our Tangled Text Protocol is so close to real HTTP that the server needed only a few extra lines (look at the bottom of webserver.py) to answer a real browser: turn TTP/1 into HTTP/1.0, rename Type and Length to Content-Type and Content-Length, end lines with CR LF, and translate our tags into HTML. Watch terminal 1 while you click; the real browser’s requests show up marked HTTP.

You can also see the real HTTP request your browser sends, headers and all, using nc as a fake server. Stop webserver.py first (Ctrl+C), then:

$ nc -l 7006 # now visit http://localhost:7006/hello in your browser; the request appears here: GET /hello HTTP/1.1 Host: localhost:7006 User-Agent: Mozilla/5.0 (Macintosh; Intel Mac OS X 10_15_7) … Accept: text/html,application/xhtml+xml,… …

Compare it with the TTP request earlier in this chapter. It has the same shape: a method, a path, a version, then headers and a blank line. (The browser will sit there waiting for an answer that never comes; press Ctrl+C in the terminal to end it.)

Stretch goals

  • Our browser fetches every image, even though it can only print a line about it. Add a cache: remember the bytes of images it has already fetched, and don’t fetch them again. How many requests does going back to Bob’s front page take now? What goes wrong if Bob changes the picture?
  • Add a LIST feature to webserver.py: if someone asks for a folder that has no index.mu, generate a markup page listing its files as links.
  • Write a “spider”: a program that starts at ttp://bob/index.mu, follows every link it finds, and prints a list of all the pages it can reach and all the broken links. Congratulations, you’ve written the core of a search engine.
