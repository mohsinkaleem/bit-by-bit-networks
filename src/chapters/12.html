A computer with many doors

Alice’s packets now reach Grandpa Otto’s computer, 4.2, all the way across town. But Otto’s computer is running several programs at once: a chat program for talking to Alice, a clock that anyone can ask the time, and a chess program he uses to play Bob. When a packet arrives for 4.2, which program should get it?

Back in Chapter 4, the operating system’s mailroom delivered messages by program name: TO: SERVE. Names are clumsy, though. They’re different lengths, so they’re awkward to put in a header. And what if Otto runs two copies of the same program, like two chess games at once? They’d both be called CHESS.

Numbered mailboxes

So instead of names, we use numbers. When a program starts, it asks the operating system for a numbered mailbox, called a port. Otto’s chat program asks for port 7, the clock for port 123, and chess for port 64 (one for each square on the board). From then on, anything that arrives addressed to port 64 is handed to the chess program.

How does Alice know that Otto’s chess program is at port 64? Everyone agrees in advance. Just as everyone knows the number for the fire brigade, the town agrees that chess lives at 64 and clocks live at 123. These are called well-known ports.

Alice’s own chess program needs a port too, so that Otto’s replies can find their way back to it. But nobody needs to know it in advance, so Alice’s operating system just picks a free one at random, say 51234. The reply goes to “1.1, port 51234”.

Four numbers make a conversation

Here’s something neat. Otto’s chess program plays Alice and Bob at the same time, both on port 64. How does it keep the games apart? By looking at where each datagram came from. A move from 1.1 port 51234 belongs to Alice’s game, and a move from 1.2 port 50999 belongs to Bob’s. If Alice opens a second chess window, it gets a different port, and that’s a third game.

Nobody home

What if a datagram arrives for a port that no program is using? The operating system drops it, and as a courtesy, sends a short note back: “nobody home at port 99”. That’s exactly the “nobody home” from Chapter 4, now with numbers.

Eve could send one datagram to every port on Otto’s computer, from 1 to 65,535, and note which ones don’t say “nobody home”. What would she learn? Why might Otto not want her to?

This is called port scanning. It tells Eve which programs Otto is running, and so which ones she might try to attack. It’s one of the first things an attacker does, and one of the first things a network defender checks for.

Fire and forget

Datagrams are wonderfully simple. There’s no setup and no goodbye: you just send one. But they come with no promises at all:

For some jobs, that’s fine. If Otto’s clock doesn’t answer within a second, Alice can just ask again. For a live game or a phone call, a late message is useless anyway, so there’s no point waiting for a resend. For other jobs, like sending a long letter, it’s not fine at all. That’s the next chapter.

Our datagram is the real User Datagram Protocol, UDP, defined in 1980 by David P. Reed in a document just three pages long. Its header is exactly our four fields: destination port, source port, length and checksum, 8 bytes in all. Port numbers are 16 bits, so they go from 0 to 65,535. Real well-known ports include 53 for looking up names (Chapter 14), 123 for clocks, and 443 for secure websites.

Programs ask the operating system for ports through an interface called sockets, invented for Berkeley Unix in 1983 and now used by almost every operating system. In Python, socket.socket(AF_INET, SOCK_DGRAM) makes a UDP socket, bind() asks for a port, and sendto() and recvfrom() send and receive datagrams. On most systems, ports below 1024 are reserved for programs with administrator rights, which is why our lab uses 7012, 7064 and 7123 instead of 7, 64 and 123.

What’s next?

Alice wants to send Grandpa Otto her whole school report, fifty pages of it, as a few hundred datagrams. Some will be lost, some will arrive out of order, and a few might arrive twice. And if she sends them too fast, Otto’s mailbox will overflow, as you’ll see in the lab. In the next chapter, we’ll build reliable delivery on top of unreliable datagrams.

otto.py is Grandpa Otto’s computer: four programs, each with its own real UDP port on your computer. dgram.py sends datagrams to them. You’ll need two terminals.

1. Start Otto’s computer

$ cd labs/ch12 $ python3 otto.py chat is listening on 127.0.0.1:7012 clock is listening on 127.0.0.1:7123 slowpoke is listening on 127.0.0.1:7099 chess is listening on 127.0.0.1:7064 Otto's computer is ready. Ctrl-C to stop.

2. Send some datagrams

$ cd labs/ch12 $ python3 dgram.py 7123 sent 16 bytes from 127.0.0.1:58830 to 127.0.0.1:7123 reply from 127.0.0.1:7123: It's 19:21:27 at Otto's. $ python3 dgram.py 7064 e4 sent 2 bytes from 127.0.0.1:55997 to 127.0.0.1:7064 reply from 127.0.0.1:7064: game #1, move 1: you played e4, I play e5 $ python3 dgram.py 7064 Nf3 sent 3 bytes from 127.0.0.1:63496 to 127.0.0.1:7064 reply from 127.0.0.1:7064: game #2, move 1: you played Nf3, I play e5 $ python3 dgram.py 7064 d4 --from-port 50001 reply from 127.0.0.1:7064: game #3, move 1: you played d4, I play e5 $ python3 dgram.py 7064 c4 --from-port 50001 reply from 127.0.0.1:7064: game #3, move 2: you played c4, I play Nc6 $ python3 dgram.py 7055 hello sent 5 bytes from 127.0.0.1:64856 to 127.0.0.1:7055 nobody home! 3. Look at the mailboxes from outside

With otto.py still running, list its ports (on Linux, ss -ulpn), and talk to the clock with nc:

$ lsof -nP -iUDP:7000-7200 COMMAND PID USER FD TYPE DEVICE SIZE/OFF NODE NAME Python 84991 alice 4u IPv4 0xf7233dd1bc41d7ed 0t0 UDP 127.0.0.1:7012 Python 84991 alice 5u IPv4 0xa006c17cc8e37a1c 0t0 UDP 127.0.0.1:7123 … $ echo hi | nc -u -w1 127.0.0.1 7123 It's 19:21:46 at Otto's.

4. Fire and forget, for real

Slowpoke handles each datagram slowly, and has a small mailbox. Fire 5,000 numbered datagrams at it without waiting:

$ python3 dgram.py 7099 --blast 5000 fired 5,000 datagrams from port 51066 without waiting for anything reply: slowpoke got 147 of 5,000 datagrams; 4,853 never arrived (97%), 0 arrived out of order

Nothing went wrong on the “network” (it never even left your computer). Slowpoke’s mailbox simply filled up, and the operating system threw the rest away, telling nobody. On a Raspberry Pi running Linux, only 54 got through. UDP has no way to say “slow down”.

Experiments

  • Try python3 dgram.py 7123 --host 192.168.1.250 (pick an address on your network where there’s no computer). Why do you get silence instead of “nobody home”?
  • In otto.py, remove the time.sleep in slowpoke, or make its mailbox bigger (SO_RCVBUF). How many datagrams survive now?
  • Run otto.py in a second copy. What error do you get, and why? Check with lsof or ss.
  • Write a “weather station” that sends Otto’s chat a numbered temperature reading every second. Stop and restart otto.py while it runs. What happens to the readings sent while Otto was down?
