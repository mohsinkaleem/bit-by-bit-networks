Every idea in this book has a real counterpart running on your computer right now, and the command line is the easiest way to look at it. This guide collects the most useful networking commands for macOS and Linux, grouped by topic. Each entry has a table of the commands side by side, then real output with the interesting parts numbered and explained.

The chapters point here from their “At the command line” boxes, and the chip next to each command shows which chapters it belongs to. This guide grows with the book. It covers every chapter of the book.

Before you start

Opening a terminal. On a Mac, open Terminal from Applications → Utilities (or press ⌘-Space and type “terminal”). On Linux, look for Terminal in your applications menu. On Ubuntu, Ctrl-Alt-T opens one. In the examples, lines starting with $ are what you type (don’t type the $ itself), and everything else is what the computer prints.

Getting help. Almost every command has a manual page: man ping opens it, the arrow keys scroll, /word searches, and q quits. Many commands also print a short summary with --help or -h. To stop a command that keeps running, like ping, press Ctrl-C.

Old tools and new tools on Linux. For decades, Unix systems used ifconfig, netstat, arp and route to look at the network. Linux has since replaced them with two newer tools, ip and ss, and many Linux systems no longer install the old ones at all. macOS still uses the old names, but its versions come from BSD Unix, and their options don’t always match the Linux versions. That’s why the same job often needs different commands on the two systems, and why this guide shows both.

Missing a command? On a Mac, install extra tools with Homebrew: brew install mtr. On Debian, Ubuntu and Raspberry Pi OS use sudo apt install xxd, and on Fedora sudo dnf install. sudo runs one command with administrator rights, and it will ask for your password. Nothing in this guide needs it unless it says so.

The examples below were captured on a MacBook and on a Raspberry Pi running Debian 13, both on the same home network. Your addresses, names and numbers will be different, and that’s part of the fun.

Bits and bytes

A hex dump shows every byte of a file, or of whatever a command prints, as hexadecimal numbers alongside any readable text. It’s the quickest way to see what’s really inside. xxd can also show individual bits, and turn hex back into bytes.

It comes from the vim editor. $ printf 'HI' | xxd -b ⟦1:00000000:⟧ ⟦2:01001000⟧ 01001001 ⟦3:HI⟧ $ printf 'HI BOB\n' > hi.txt $ xxd hi.txt 00000000: ⟦4:4849⟧ 2042 4f42 ⟦5:0a⟧ HI BOB⟦6:.⟧ 1 | The offset: how many bytes into the data this line starts, counted in hex. 2 | The letter H as 8 bits. H is number 72 in ASCII, and 72 = 64 + 8 = 01001000 (Chapters 1 and 5). 3 | The same bytes as text, wherever they’re printable. 4 | Without -b, each byte is two hex digits, grouped in pairs: 48 is H, 49 is I. 5 | 0a is the newline character that \n added: the invisible “end of line”. 6 | Bytes that aren’t printable characters show up as dots.

A file’s name is just a label, and anyone can rename cat.png to cat.txt. file ignores the name and looks at the first few bytes instead, where most formats put a magic number (Chapter 5). It can also print the media type that a web server would send.

Checking data

A SHA-256 fingerprint is 256 bits long, and changing even one bit of the file changes it completely. Websites often publish the fingerprints of their downloads, so you can check that you got exactly the right file. Unlike the CRC, it’s designed so that nobody can craft a different file with the same fingerprint (Chapter 31).

== Fingerprint a file mac: shasum -a 256 hi.txt linux: sha256sum hi.txt == Check files against a list of fingerprints mac: shasum -a 256 -c SHA256SUMS linux: sha256sum -c SHA256SUMS == Are two files identical? Where do they differ? both: cmp a.bin b.bin $ shasum -a 256 hi.txt ⟦1:fba51340df5c4e635dbfeac1b9457b417d71718cc7965bd4fc53113c026eff27⟧ hi.txt $ sha256sum hi.txt fba51340df5c4e635dbfeac1b9457b417d71718cc7965bd4fc53113c026eff27 hi.txt 1 | 64 hex digits, 4 bits each, makes 256 bits. The same 7 bytes give the same fingerprint on every computer in the world.

There’s no single standard command for CRC-32, but there are two good tricks. The Mac’s cksum can use the CRC-32 from Ethernet and ZIP files. And every gzip file ends with a CRC-32 of its contents, followed by the length, so you can make one and read the last 8 bytes.

== CRC-32 (the Ethernet and ZIP one) mac: cksum -o 3 hi.txt linux: python3 -c "import zlib,sys; print(zlib.crc32(sys.stdin.buffer.read()))" < hi.txt == A trick that works everywhere both: gzip -c hi.txt | tail -c 8 | xxd == The POSIX checksum (a different CRC!) both: cksum hi.txt $ printf 'HI BOB' | cksum -o 3 ⟦1:993367676⟧ ⟦2:6⟧ $ printf 'HI BOB' | gzip -c | tail -c 8 | xxd 00000000: ⟦3:7c96 353b⟧ ⟦4:0600 0000⟧ |.5;.... 1 | In decimal. Convert it with python3 -c "print(hex(993367676))" and you get 0x3b35967c, exactly what checks.py demo "HI BOB" printed in Chapter 10. 2 | The number of bytes that were checked. 3 | The same CRC in gzip’s trailer, 3b 35 96 7c written backwards: gzip stores numbers little-endian (Chapter 5’s eggs!). 4 | The length, 6, also little-endian.

Plain cksum, with no options, uses the CRC from the POSIX standard. It’s the same long-division idea with a different divisor and bit order, so its answers won’t match zlib’s.

Every way your computer can connect to a network is an interface: the Wi-Fi card, an Ethernet port, and the pretend “loopback” interface that programs on the same computer use to talk to each other. This is how to see them, along with each card’s address (Chapter 8) and its maximum packet size (Chapter 10).

Addresses and routes

Besides its card address, every interface that’s connected to a network has a network address (Chapter 11), and a netmask or prefix length that says how many of its bits are the network part.

A static route is one you type in yourself (Chapter 23): “to reach this network, go through that router”. It’s handy for a lab, a VPN, or a second router at home. Routes you add this way vanish when the computer restarts, which makes experimenting safe. A blackhole route throws matching packets away, which is how networks stop traffic to an address under attack. All of these need sudo.

arping sends ARP “who has?” questions and times the answers, the way ping does with ICMP. Because ARP never leaves your own network, it works even for devices that ignore pings. Encryption and certificates

openssl does the rest of Chapter 31 on the command line: fingerprints with any hash, HMACs (a fingerprint mixed with a secret key, which only someone with the key can make), and random bytes good enough for keys and nonces. For plain fingerprints, shasum is simpler. On a Mac, /usr/bin/openssl is Apple’s LibreSSL; brew install openssl gets the real OpenSSL, which prints slightly different names.

Faking a bad network

Linux can pretend a link is worse than it is. netem, the network emulator, is a queue (Linux calls them “qdiscs”; Chapter 28 met the queues in routers) that holds packets back for a while, shuffles them, loses some, or limits their speed, on the way out of an interface. Watching packets

tcpdump shows you the packets passing through a network interface, as they happen, decoded layer by layer. It’s the single most useful tool for seeing what a network is really doing. Watching live needs administrator rights (sudo), because it can see everyone’s traffic on that interface. Reading a saved capture file doesn’t.

tshark is the command-line half of Wireshark. It reads and captures the same files as tcpdump, but it decodes thousands of protocols, can filter on any field by name (display filters, after -Y), and can print statistics. On a Mac, brew install wireshark installs it (or install the Wireshark app, which includes it); on Debian and Raspberry Pi OS, sudo apt install tshark.
